## Method and observations

Both appliances use the shipped XO Lite `#/xoa-deploy` Custom URL flow.
The shared preview browser returned `ERR_CERT_AUTHORITY_INVALID` twice;
the existing Playwright fallback kept the actual deployment page open until
success. XO backup and recovery operations use the installed JSON-RPC API.

A new halted VM with no VIF and one 1 GiB disk provides a controlled fixture.
A separate 6 GiB VDI, mounted as a local file remote, holds the full VM backup
and XO metadata. No baseline VM participates in these tests.

- Full VM backup: success, backup log records 268,527,069 transferred bytes.
- Restore: new VM stayed halted with no VIF. Whole-disk SHA256 equals the
  source: `28572f707d4cc882ab77bd707bce6fd1e48a9506bb6cf0e2724c40d823b73353`.
- XO metadata backup: success to the separate backup disk.
- Appliance-loss recovery: pass. The original appliance and system disk were
  removed; the backup VDI survived, detached. A fresh XO Lite deployment had
  zero backup jobs and zero server connections. After mounting the surviving
  disk, a temporary remote discovered the XO metadata backup; metadata restore
  returned true and closed the API connection. A fresh connection read back
  the original admin ID, connected host ID, full-backup job, disabled schedules
  and original remote ID. Default admin login was rejected.
- Post-recovery VM restore: pass. The fresh appliance discovered and restored
  the original backup. The new halted, zero-VIF VM's entire disk again matched
  the source checksum above. The source also retained its original checksum.

The first metadata harness call created a job but expected a scalar job ID
where the API returned an object. No metadata run occurred in that call.
The harness selected the existing job from inventory and ran it successfully;
this was a test harness correction, not a product failure.
