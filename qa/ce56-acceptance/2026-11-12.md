Why the appliance rows are blocked. Both appliance jobs take no environment
or target parameter. `test/xoa-deploy-test` takes `BRANCH`, `TAG`,
`XVA_URL`, `XVA_SHA256`, `IMAGE_SHA`; `test/xoa-update-test` takes `BRANCH`,
`TARGET_NEVRA`, `TARGET_SHA256`, `BASE_XVA_URL`, `BASE_XVA_SHA256`. Their
driver reads the host from the registry: `agent/appliance-lib.sh:6`,
`HOST=$(jq -r .test.xcpng_host ...)`, which is `192.168.0.10`, the host that
runs ce36. The documented deploy test also imports through XAPI and writes
the xenstore keys XO Lite's Deploy XOA writes; it does not drive the XO Lite
browser flow, and `test/xolite-ui-test` only asserts that the Deploy XOA
dialog offers the HomeLab Edition sources.

So a run of either job today would be evidence about a ce36 host, and this
record does not report it as ce56 evidence. For completeness, the runs
behind the XVA and RPM ledger verdicts are `test/xoa-deploy-test` #36 and
`test/xoa-update-test` #48, both 2026-11-09; the deploy test has since run
once more on the same ce36 host (#37, SUCCESS, 2026-11-10 19:43Z), and
`test/xoa-update-test` #49 (2026-11-09 20:28Z) ended FAILURE with exit 255
from its driver. None of these is about ce56.

What each unrun or blocked path would need:

- Appliance deploy and update on a ce56 host: either an
  `ENVIRONMENT`-style parameter resolved from `config/environments.json`
  threaded through `agent/appliance-lib.sh` and
  `agent/appliance-resources.sh` (with the target's capacity gate and its
  own lock), which is a code change to the test in `jenkins-infra`; or a
  nested XCP-ng host inside the validation VM to hold the appliance as a
  second-level guest, which is part of the same code change; or an
  owner-approved reinstall of the bare-metal Test host `192.168.0.10` to
  ce56, after which both jobs run unmodified. The last of these is an owner
  decision and was not taken: that host's local storage holds the
  validation VM, the documentation lab guests, the `ga-gold-*` images and
  other lab cells, and recreating them is a manual procedure.
- Guest boot from its own disk: a job that creates a guest with a bootable
  disk, starts it and asserts it boots. None exists, and none was written
  here to keep the run inside existing jobs.
- Host Patches tab path: a job that drives `updater.py` or `yum update` on
  the host and checks the result. None exists.

## Known limits that stay as they are

Issues #389 (the bootstrap account can sign in until first setup completes),
#388 (a configuration import can restore the default admin) and #392
(auto-update can mask a pending reboot) are accepted for this beta. Nothing
on ce56 reproduced or contradicted them, because the appliance path that
would exercise #389 and #392 could not run on a ce56 host. That is a gap,
not a pass.
