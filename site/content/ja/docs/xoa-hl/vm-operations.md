最初の練習では、本番データを含まない使い捨ての VM を使用します。管理者として **XOA-HL アプライアンス**にログインし、VM、ホスト、ストレージが利用できることを確認してください。重要な VM を変更する前に、独立した[バックアップと復元テスト](/docs/xoa-hl/backup-restore/)を用意します。

{{< callout type="info" >}}
イメージ `xoa-image-20261009-5f33c81`、パッケージ `v5.113.2_e281c536-ce38`、XO 5.113.2 を対象としたソース確認済みのプレビューです。このアプライアンスでの電源操作、スナップショットへの復帰、クローン、CPU・メモリの変更、削除のテストは未完了です。後のリリースでは動作が異なる場合があります。
{{< /callout >}}

## 1. 起動、停止、再起動

対象 VM を開きます (`/#/vms/<id>/general`)。停止中なら **Start** を選び、状態とコンソールでゲストの起動を確認します。実行中の **Stop** と **Reboot** は、最初にゲストの正常なシャットダウンまたは再起動を要求します。

ゲスト側の機能が不足している場合や操作がブロックされている場合、XO は強制操作またはブロックの回避を確認することがあります。続行する前にメッセージを読んでください。強制停止や強制再起動ではゲストのデータを失う可能性があります。可能ならゲスト内でシャットダウンします。タスク実行中に繰り返しクリックしないでください。完了後に VM の状態とコンソールを確認します。成功通知だけではアプリケーションの正常動作を確認できません。

## 2. 保護方法を選ぶ

| 種類 | 目的と制限 |
| --- | --- |
| スナップショット | VM のある時点の状態。元のストレージに依存し、独立したバックアップではない |
| 高速クローン | ストレージ効率のよいコピーを使う別の VM。同じストレージの喪失には備えられない |
| バックアップ | 別に保存する復旧用コピー。隔離した復元で確認する |

VM の変更に伴い、スナップショットとクローンもストレージを消費します。SR の空き容量を確認し、削除するのは確実に識別したテスト用オブジェクトだけにしてください。稼働中のスナップショットはアプリケーションの整合性を保証しません。

## 3. 停止中のスナップショットを作成する

1. 使い捨てのゲストをシャットダウンし、停止状態を確認します。VM の識別情報、ディスク一覧、後で比較する重要でないファイルや設定を記録します。
2. **Snapshots** (`/#/vms/<id>/snapshots`) を開き、**New snapshot** を選びます。この練習ではメモリの保存を選びません。
3. 完了を待ち、日時で新しい行を特定して、分かりやすいテスト名に変更します。タスクのエラーと空き容量を確認します。

作成に失敗したら、エラーを保存し、容量と接続を確認してから再試行します。通知がないだけで、スナップショットが作成されなかったと判断しないでください。

## 4. テスト VM をスナップショットに戻す

重要でないテストデータを変更し、ゲストを再び停止します。記録したスナップショットの **Revert VM to this snapshot** を選びます。この操作は VM の現在の状態を置き換えます。確認画面には現在の状態を先にスナップショットとして保存する選択肢があり、このリリースでは初期状態で有効です。選択と空き容量を確認してください。

実行中に取得したスナップショットに戻すと、XO が VM を起動または再開する場合があります。ここでは停止中に取得したものを使い、手動で起動する前に結果の電源状態を確認します。必要に応じてゲストを起動し、記録したファイルや設定、ディスク一覧を確認します。アプライアンスや本番 VM では練習しないでください。

## 5. 隔離した高速クローンを準備する

停止中の使い捨て VM で **Fast clone** を選びます。新しい VM（初期名の末尾は `_clone`）を探し、異なる識別情報を記録して名前を変更します。[継承したネットワークインターフェースをすべて削除する](/docs/xoa-hl/storage-networks/)か、外部の隔離を確認するまでは停止状態を保ちます。MAC アドレスの自動生成だけでは、コピーされた IP アドレス、資格情報、アプリケーションの識別情報は変わりません。

その後クローンを起動してコンソールを確認します。重複した識別情報を解消し、隔離を確認してからネットワークを再接続してください。エラー後にクローンが見つからなければ、再試行前に一覧とタスクを確認します。この練習ではライブマイグレーション、メモリを含むスナップショット、SR 喪失後の復旧を検証しません。

## 6. 停止中の VM のリソースを変更する

メンテナンス時間を確保し、コンソールにアクセスできる使い捨てのゲストを使用します。変更前に ID、ゲストの状態、現在の CPU・メモリ値と上限・下限を記録してください。ホスト・プールの容量とゲストの要件を確認します。このガイドでは、すべての環境に共通する CPU 数やメモリ容量を指定しません。

{{< callout type="warning" >}}
この練習ではゲストを正常にシャットダウンし、**Halted** を確認してから変更します。実行中に変更できない値を編集すると、再起動または強制再起動を提案する場合があります。ここではその確認をキャンセルし、先に停止してください。上限を増やしてもホストのリソースが確保されるとは限りません。メモリを減らすとゲストが起動できなくなる場合があります。
{{< /callout >}}

1. **詳細設定** (`/#/vms/<id>/advanced`) を開き、**CPU limits** と **Memory limits (min/max)** を記録します。この固定バージョンの日本語カタログでは、この二つのラベルは英語です。CPU の行は現在値／最大値を示し、VM が実行中でなければ最大値を編集できます。予定する CPU 数が記録した最大値を超える場合は、VM を停止した状態で先に最大値を増やします。
2. **一般** (`/#/vms/<id>/general`) を開きます。CPU 数をクリックし、予定する正の整数を入力して **Enter** を押します。完了を待って再読み込みし、値を確認してから次の変更を行います。インライン入力はフォーカスを失う際にも保存される場合があります。別の場所をクリックしても、安全に編集をキャンセルできるとは限りません。
3. メモリ値をクリックし、容量・単位の入力で予定する値を設定して **Enter** を押します。表示値は設定された**動的最大値**であり、ゲスト内で現在使用している RAM の測定値ではありません。既存の範囲に応じて、バックエンドは固定メモリ構成または動的メモリの制限を変更します。
4. **一般**と**詳細設定**を再読み込みし、変更後のすべての値を記録します。CPU 数は最大値以下にします。メモリの範囲は、静的最小値 ≤ 動的最小値 ≤ 動的最大値 ≤ 静的最大値の順序を保つ必要があります。ソースでは関連する制限も調整される場合があるため、クリックした項目だけが変わったとは判断しないでください。この練習は、ホットプラグ、負荷時の動的メモリ、CPU トポロジーの調整を検証するものではありません。
5. テスト VM を起動し、コンソール、ゲストから見える CPU・メモリ、アプリケーションの状態を確認します。起動できない場合や値が想定と異なる場合は停止状態に保ち、タスクのエラーを保存して、同じ管理された作業時間内で記録した構成に戻します。すべての制限を確認し、原因を特定してから再試行してください。成功通知だけでは十分ではありません。

編集でエラーが出た場合は、再試行前に実際の値を確認します。関連する変更はアトミックなトランザクションとして保証されず、拒否されたからといってすべての値が元に戻ったとは限りません。[トラブルシューティング](/docs/xoa-hl/troubleshooting/)と記録した変更前の状態を用意してください。

## 7. 使い捨ての VM だけを削除する

{{< callout type="warning" >}}
**Remove** は VM に対する破壊的な操作であり、ディスクの切断や取り外しとは異なります。この固定バージョンの通常の確認画面には、ディスクを保持する選択肢はありません。削除では VM のスナップショットも処理され、接続されたディスクの VDI の削除が試みられます。データやスナップショットを残す必要がある場合は、確認する前に作業を止め、別の保存手順を計画してください。この VM のスナップショットは独立した復旧用コピーではありません。
{{< /callout >}}

1. 対象が使い捨て VM であり、アプライアンス、元のゲスト、テンプレート、似た名前の別の VM ではないことを確認します。ID、接続されたディスクの ID・SR、スナップショットを記録します。削除前にバックアップ・レプリケーションのスケジュールと、共有ディスクを使用する他の VM を確認してください。重要なデータについては、先に独立した[バックアップと隔離した復元テスト](/docs/xoa-hl/backup-restore/)を完了します。
2. ゲストを正常にシャットダウンし、**Halted** を確認します。削除のバックエンドは実行中やサスペンド中の VM を強制停止する場合があります。**Remove** を正常なシャットダウンの代わりに使わないでください。
3. **詳細設定**を開き、**Remove** を選びます。VM とディスクの警告を読み、予定した対象だけを確認します。保護やブロックを無視して削除する二回目の確認が出た場合は、この練習を中止し、強制再試行を承認する代わりに保護の理由を調べてください。
4. 完了を待ち、VM、スナップショット、SR のディスク一覧を再読み込みします。記録した ID と削除タスク・エラーを確認してください。このソースの処理では、別の非コントロールドメイン VM にまだ接続されている共有 VDI は削除をスキップします。この例外はすべてのディスクを保持する保証ではありません。スナップショットや VDI の後処理エラーは、削除全体を失敗にせずログに記録される場合があります。VM が一覧から消えたり成功通知が出たりしても、後処理がすべて完了したとは判断できません。
5. 元の VM、他のゲスト、必要な独立したバックアップが引き続き利用できることを確認します。[ディスク管理の操作の違い](/docs/xoa-hl/storage-networks/)と記録した ID を使い、残ったテスト用オブジェクトを一つずつ確認してください。孤立して見えるディスクを一括削除したり、空き容量を戻すために強制操作を再試行したりしないでください。このガイドでは削除を取り消せません。削除したゲストデータの復旧には、別に検証した復旧用コピーが必要です。

途中で削除が失敗した場合は、残った VM・ディスク・スナップショット一覧とエラーを保存します。同じような名前で VM を作り直しても、同じオブジェクトにはなりません。追加の削除を行う前に、バージョンと機密情報を除いた ID を添えて[問題を報告](/docs/xoa-hl/troubleshooting/)してください。
