VM の日常的な操作を説明します。コンソールの利用、VM の起動と停止、スナップショットの作成と復元、クローンとコピー、CPU とメモリの変更、VM の削除です。どの作業も、本番データのないテスト用 VM で、**XOA-HL アプライアンス** に管理者としてログインして練習してください。重要な VM を変更する前に、独立した[バックアップと、試した復元](/docs/xoa-hl/backup-restore/)があることを確認します。

## VM のコンソールを使う {#vm-console}

コンソールは、VM の画面をブラウザーに表示します。VM の **操作** 権限が必要です。Viewer の権限だけでは使えません。コンソールにゲストの IP アドレスは不要ですが、ブラウザーからアプライアンスへ、アプライアンスからホストへ接続できる必要があります。テスト用 VM のネットワークの隔離は、そのままにしておきます。

1. VM の **コンソール** タブ（`/#/vms/<id>/console`）を開きます。正しい VM で、状態が **Running** であることを確認します。一時停止やサスペンドを含め、それ以外の状態では **Console is only available for running VMs.** と表示されます。VM は計画した[電源操作](#vm-power)で起動します。コンソールを出すためだけに強制再起動しないでください。
2. ログイン画面、インストーラー、既知のアプリケーションなど、想定した画面を待ちます。ここで入力する認証情報はゲストのもので、XOA-HL やホストのものではありません。
3. ポインターをコンソールの領域に入れると、キーボードとマウスがゲストに送られます。外に出すと元に戻り、XO のショートカットも使えるようになります。入力を試すには、テスト用ゲストのテキストエディターで `console-test` などの無害な文字列を入力し、削除します。シェルのコマンドやパスワード欄では試さないでください。画面が見えるだけでは、入力が届くとは限りません。
4. 大きな画面では、表示倍率は **100%** から始まります。変わるのはブラウザー内の表示で、ゲストの解像度ではありません。小さな画面では表示されないことがあります。**Hide infos** と **Show infos** は XO のヘッダーの表示を切り替えるだけで、ゲストを停止したり全画面にしたりするものではありません。
5. 終わったらタブを離れます。コンソールの接続は閉じますが、ゲストは停止しません。接続中に VM が再起動した場合は、タブを開き直して新しい画面を表示します。XO は再起動後の切断に気付かないことがあり、自動の再接続が続いていてもゲストが正常とは限りません。

**確認:** 正しい実行中のゲストが表示され、テストの入力が届き、ポインターを外すと XO の操作に戻れ、VM は想定どおりの状態のままです。

### クリップボードとリモートクライアントのボタン

- クリップボードのテキスト欄の内容は、少し待つとゲストのクリップボードに送られます。**コピー** は、欄の文字列を自分のコンピューターのクリップボードにコピーします。複数行のボタンは **クリップボードに送信** を開きます。無害な文字列で試し、ゲスト内での貼り付けは別に確認してください。欄やスクリーンショットに、パスワードや個人情報を入れないでください。
- **SSH**、**SSH as…**、**RDP** は、ゲストが報告する IP アドレスを使って、自分のコンピューターの `ssh://` または `rdp://` のハンドラーを開きます。IP アドレスが報告されるとボタンが表示されます。ただし、クライアントがインストールされていること、ゲストでサービスが動いていること、ネットワークで許可されていることまでは分かりません。これらのボタンはコンソールの修復や代わりにはなりません。
- **Ctrl+Alt+Del** は確認の後、このキーの組み合わせをゲストに送ります。ゲストによっては再起動することがあります。このテストでは取り消してください。接続のテストには使いません。ISO の選択欄は、ゲストにマウントするメディアを変更します。変更する前に[最初の VM を作成する](/docs/xoa-hl/create-vm/)を参照してください。

### コンソールが真っ暗、または応答しない場合

1. **VM が実行中でない、またはコンソールが無効。** まず状態とメッセージを読みます。`disable_pv_vnc=1` が設定された実行中の VM では、画面の代わりに **このVMのコンソールを無効化します** と表示されます。これは状態を示すメッセージで、有効にするボタンではありません。VM を変更する前に、この設定の担当者に確認してください。ツールのインストールや再起動では、コンソールは有効になりません。
2. **接続が開かない、または切断を繰り返す。** アカウントに VM の操作権限があるか、ホストへの接続が正常かを確認します。ブラウザーの開発者ツールで、`/api/consoles/<id>` で終わる WebSocket のリクエストを探し、エラーや状態を控えます。アプライアンスの前にリバースプロキシがある場合は、通常のページ要求だけでなく WebSocket のアップグレードを通す必要があります。ブラウザーからアプライアンスへの接続（TLS を含む）と、アプライアンスからホストへの接続は分けて確認します。ゲストの IP アドレス、SSH サーバー、ファイアウォールは、コンソールの経路ではありません。問題は、その経路の担当者と一緒に直します。一時しのぎに VNC のポートを公開したり、証明書の検証を無効にしたりしないでください。
3. **接続はするが、画面が真っ暗、または固まっている。** 正しい VM を開いているか、本来何が表示されるはずか、最近の電源操作を確認します。再起動の後はタブを開き直します。画面が真っ暗な原因はゲスト側のことも接続側のこともあるため、ゲストに合わせた対処を試す前に、見えている状態を記録します。画面が黒いというだけで、再起動を繰り返したり、再インストールや起動メディアの変更をしたりしないでください。
4. **画面は映るが、入力やクリップボードが使えない。** ポインターを一度外に出してから戻し、エディターでのテストを繰り返します。ブラウザーや OS がキーを横取りしていないか、ゲストがそのクリップボード操作に対応しているかを確認します。SSH や RDP の問題は別に扱います。[問題の報告](/docs/xoa-hl/troubleshooting/#report-a-problem)には、ブラウザーとバージョン、VM とホストの ID、時刻、電源状態、正確なメッセージ、接続エラーを、個人情報を除いて書きます。ブラウザーの生のトレースは公開しないでください。Cookie、トークン、クリップボードの文字列、ゲストの画面には機密情報が含まれることがあります。

## VM の起動、停止、再起動 {#vm-power}

まず VM の **一般** タブ（`/#/vms/<id>/general`）で、管理エージェントが検出されているか確認します。管理エージェントがなければ、XO からゲストを正常にシャットダウンしたり再起動したりできません。[ゲストツールの状態とインストール](/docs/xoa-hl/guest-tools/#guest-tools-status)を参照してください。

D3 で試した管理エージェントのないゲスト 1 台では、正常な停止要求が 1200 秒待った後、`VM_SHUTDOWN_TIMEOUT` で失敗しました。VM は **Running** のままでした。再起動は「VM lacks feature」で即座に拒否されました。強制停止では数秒で **Halted** になりました。

停止中の VM は **仮想マシンの起動** を選び、状態とコンソールを確認します。正常な停止や再起動の前に、ゲストツールをインストールしてエージェントを確認するか、ゲスト内からシャットダウンします。強制停止は、ゲストをシャットダウンできない場合だけ使います。電源を引き抜くのと同じで、データが失われることがあります。

確認画面を読んでから続けます。タスクの実行中に何度もクリックしないでください。完了したら VM の状態、コンソール、アプリケーションを確認します。成功のメッセージだけでは、アプリケーションの正常動作は分かりません。

## スナップショット、クローン、コピー、バックアップの違い {#protection-types}

| 方法 | 得られるものと限界 |
| --- | --- |
| スナップショット | ある時点の VM。ディスクと同じ場所に保存されます。独立したバックアップではありません |
| 高速クローン | 元の VM とストレージを共有する別の VM。そのストレージが失われると守れません |
| フルコピー | 選んだ SR にディスクをコピーした別の VM。使う前に、データ、置き場所、隔離を確認します |
| バックアップ | 別に保存する復旧用のコピー。隔離した復元で確かめます |

VM が変化するにつれて、スナップショットとクローンが使うストレージは増えます。SR の空き容量を確認し、はっきり特定したテスト用のオブジェクトだけを削除してください。実行中の VM のスナップショットは、アプリケーションの整合性が保証されません。

## 停止中の VM のスナップショットを作成する <span class="hx:absolute" id="3-停止中のスナップショットを作成する"></span> {#stopped-snapshot}

通常のディスクを持ち（共有ディスクやパススルーデバイスはなし）、コンソールが使えるテスト用 VM を使います。バックアップとレプリケーションのスケジュールを止め、実行中のタスクが終わるまで待ちます。必要なデータは、独立した復旧用のコピーを残します。実行中の VM のスナップショット、メモリを含むスナップショット、アプリケーションの整合性は扱いません。

1. ゲストで `snapshot-A` と書いた無害なファイルを作り、チェックサムを控えます。ゲストを正常にシャットダウンし、VM が **Halted** であることを確認します。
2. VM の UUID、各ディスク（VDI）の ID・SR・サイズ、既存のスナップショットの UUID、SR の空き容量を控えます。次に、[テスト用 VM のネットワークインターフェース（VIF）をすべて削除](/docs/xoa-hl/storage-networks/)し、一覧が空であることを確認します。以降はコンソールを使います。
3. 各ディスクの名前を確認します。名前に `[NOSNAP]` を含むディスクは、スナップショットから外されることがあります。これはディスク名の一部で、VM のタグではありません。外されたディスク、共有ディスク、パススルーデバイスには別の手順が必要です。既存のルールを回避するためにディスク名を変えないでください。スナップショット、その後の書き込み、復元前に作られる追加のスナップショットのための容量を確保します。
4. **スナップショット**（`/#/vms/<id>/snapshots`）を開き、**New snapshot** を 1 回だけ選びます。名前を聞かれずに、すぐにスナップショットが作成されます。初期名は VM 名と日時です。**New snapshot with memory** は使いません。
5. 待ってから一覧を更新します。**Creation date** で新しい行を見つけ、行のコピーボタンで UUID をコピーします。この UUID を控えます。名前や時刻だけでは足りません。
6. 名前を `lab-snapshot-A` に、説明を短いテスト用のメモに変更します。この版の画面では、説明の列の見出しも **Name** と表示されるため、列の位置で区別してください。更新して、両方の値を確認します。スナップショットのディスクと SR をメモと比べ、エラーと空き容量を確認します。スナップショットのディスク ID は新しくなるため、ID ではなく、対象のディスクとサイズを比べます。

**確認:** 特定したスナップショットが 1 つあり、対象のディスクを含んでいます。元の VM は停止中で、VIF はありません。

作成や名前の変更に失敗した場合は、再試行の前に、エラーと実際の VM、スナップショット、ディスクの一覧を保存します。ID や通知がなくても、何も作られていないとは限りません。名前の変更に失敗しても、スナップショットは取り消されません。

## スナップショットに戻す <span class="hx:absolute" id="4-テスト-vm-をスナップショットに戻す"></span> {#snapshot-revert}

D3 では **Halted** のテスト VM でスナップショットを作成しました。その後に追加したディスクは復元後に消えました。VM は **Halted** のままで、スナップショットは残りました。ゲスト内のファイルやアプリケーションの整合性を示す結果ではありません。

[2 回目のスナップショット検証](https://github.com/Vagrantin/xcp-hl/issues/198#issuecomment-6460786269)では、VM が **Running** の間にディスクだけのスナップショットを作成しました。停止した VM に復元すると、VM は **Running** に戻りました。復元前に VM とネットワークの隔離を確認してください。スナップショットに記録された電源状態が戻る場合があります。メモリを含む（サスペンド）スナップショットは未検証です。

{{< callout type="warning" >}}
スナップショットに戻すと、VM の現在の状態が置き換わります。古いネットワークインターフェースが戻る設定も含まれます。スナップショット後の変更は失われることがあります。VM の実行中に作成したスナップショットに戻すと、ディスクだけのスナップショットオブジェクトが停止状態に見えても、VM が起動する場合があります。復元を確定する前に VM のネットワークの隔離を確認し、スナップショットオブジェクトの電源状態を判断材料にしないでください。以下の演習では、隔離したこのテスト用 VM と、停止中に作成したスナップショットだけを使います。起動前に VIF をもう一度確認します。同じ SR 上のスナップショットでは、その SR が失われたときに守れません。
{{< /callout >}}

1. 隔離したテスト用 VM を起動し、ファイルの内容を `snapshot-B` に変えて、新しいチェックサムを控えます。正常にシャットダウンし、**Halted** であることを確認します。現在のディスク、VIF、スナップショットを控えます。
2. これから使うスナップショットが、前のセクションの `lab-snapshot-A` であることを UUID で確認します。バックアップジョブが作ったスナップショットや、別の VM のスナップショットであってはいけません。
3. **スナップショット** で、その行の **Revert VM to this snapshot** を選び、**Revert your VM** の確認画面を読みます。**Snapshot before** はオンのままにし、先に空き容量を確認します。初期状態でオンのこの項目は、戻す前に現在の状態を別のスナップショットとして保存します。独立したバックアップではなく、元に戻せることも保証しません。VM、隔離、空き容量に不安があれば取り消します。
4. 1 回だけ確定して待ちます。更新して、戻したスナップショットの UUID、新しい「戻す前」のスナップショットの UUID、電源状態、ディスク、VIF、エラーを控えます。「戻す前」のスナップショットが失敗すると、XO は戻す操作を要求しません。その後で戻す操作が失敗すると、「戻す前」のスナップショットが残ることがあります。再試行の前に実際の状態を確認し、原因の分からないエラーを避けるために **Snapshot before** をオフにしないでください。
5. VM を起動する前に、**Halted** であり、VIF の一覧が空であることを確認します。VIF が戻っていた場合は、停止したまま削除します。実行中に作ったスナップショットに戻すと、VM が自動で起動または再開することがあります。このようなスナップショットは扱いません。
6. VM を起動してコンソールを開きます。ファイルが `snapshot-A` で元のチェックサムと一致すること、ディスクとアプリケーションが動くことを確認します。VM をシャットダウンし、結果を控えます。追加された「戻す前」のスナップショットには `snapshot-B` の状態が入っています。その状態に戻すのは、別に管理して行う復元です。取り消しボタンではありません。

### テスト用のスナップショットを削除する {#snapshot-cleanup}

結果を控え、必要な独立した復旧用コピーを残したら、VM は停止したままにします。削除するのは、UUID と所有者を控えたテスト用のスナップショットだけです。

1. **スナップショット** で、その行の **Remove this snapshot** を選びます。**Delete snapshot** の確認を読み、1 つだけ確定します。**Remove selected snapshots** は使わず、バックアップジョブが作ったスナップショットは削除しないでください。VM の **Remove** と混同しないでください。
2. 待ってから、スナップショット、VM のディスク、SR の空き容量を更新します。スナップショットが消え、残すスナップショットと VM がそのままで、エラーがないことを確認します。

ディスクの後片付けでエラーが記録されても、削除全体は失敗にならないことがあります。行が消えたり成功のメッセージが出たりしても、後片付けが終わった、またはすぐに容量が空いたとは限りません。残った ID を控え、[説明のつかない残りを報告](/docs/xoa-hl/troubleshooting/)してください。孤立して見えるディスクをまとめて削除しないでください。削除したスナップショットは元に戻せません。

## 隔離した高速クローンを作る {#fast-clone}

D3 では、停止中の VM から別の識別子を持つ高速クローンができ、ディスク 1 個と引き継いだ NIC 1 個がありました。その NIC を削除するとクローンは起動しました。この検証には実行中のクローンやフルコピーの結果はありません。

1. 停止中のテスト用 VM で **Fast clone** を選びます。新しい VM（初期名の末尾は `_clone`）を探し、ID を控えて名前を変更します。
2. [継承したネットワークインターフェースをすべて削除する](/docs/xoa-hl/storage-networks/)か、XO の外で確認済みの隔離を用意するまで、クローンは停止したままにします。MAC アドレスが新しくなっても、コピーされた IP アドレス、認証情報、アプリケーションの識別情報は変わりません。
3. クローンを起動し、コンソールを確認します。重複した識別情報を解消し、隔離を確認してから、ネットワークに接続します。

エラーの後でクローンが見つからない場合は、再試行の前にインベントリとタスクを確認します。ここでは、ライブマイグレーション、メモリを含むスナップショット、SR が失われた後の復旧は扱いません。

### 同じプール内でフルコピーを作る {#full-copy}

選んだ SR にディスクの通常のコピーを作るときは、別にある **Fast clone** ではなく **仮想マシンの複製** を使います。コピーの画面にも **Fast clone** がありますが、ここでは **Full copy** を選んだままにします。高速クローンも、同じプール内のフルコピーも、独立したバックアップや試した災害復旧にはなりません。

1. 通常のディスクを持つテスト用 VM を 1 台使います。共有ディスクやパススルーデバイスは使いません。ゲストで無害なファイルとチェックサムを控えます。ゲストを正常にシャットダウンし、**Halted** を確認します。VM の ID、各ディスクの ID・SR・サイズ、VIF、スナップショットを控えます。スナップショットの履歴はこのテストに含みません。
2. **同じプールにある、別の書き込み可能な VM ディスク用 SR** を選びます。ID、空き容量、コピーを実行するホストから使えることを確認します。ISO ライブラリは使えません。コピーと今後の増加に必要な容量を確保します。画面は容量を予約も確認もしません。コピー先の SR が使えない場合は、始める前にストレージへのアクセスを直します。
3. 元の VM で **仮想マシンの複製** を選びます。**Copy VM** で、**Name** に `lab-vm-full-copy` などの一意のテスト名を入力します。初期値は `{name}_COPY` で、空欄にすると元の名前のままになります。**Full copy** が選ばれていることを確認します。
4. **Select SR** で、似た名前ではなく、控えた ID とプールで SR を選びます。一覧に他のプールが表示されることがあります。それを選ぶとエクスポートとインポートの処理になり、このテストでは扱いません。**圧縮** は **Disabled** のままにします。同じプール内のコピーは圧縮されません。
5. 1 回だけ確定し、タスクを待ちます。更新して、新しい VM を独自の ID と指定した名前で探します。**Halted** であること、ディスクの数、サイズ、新しい ID、各ディスクの SR を確認します。元の VM とディスクが変わっていないことも確認します。新しい VM が実行中だったり、何かが違ったりした場合は、作業を止めて隔離を回復してから進めます。
6. 新しい VM を停止したまま、[継承した VIF をすべて削除](/docs/xoa-hl/storage-networks/)し、初回の起動前に一覧が空であることを確認します。新しい MAC アドレスに頼らないでください。ゲストの IP アドレス、認証情報、アプリケーションの識別情報はコピーされています。
7. 隔離したコピーだけを起動し、コンソールを開いて、ファイルのチェックサム、ディスク、アプリケーションを確認します。ネットワークに接続する前に重複した識別情報を解消し、確認の間、元の VM は隔離するか停止しておきます。
8. コピーをシャットダウンします。結果を控え、[テスト用 VM を削除する](#delete-vm)に従って、コピーとそのディスクだけを削除します。元の VM と独立したバックアップは残します。

エラー、接続の切断、中断されたリクエストがあった場合は、再試行の前に、タスク、エラー、両方の VM・ディスク・スナップショットの一覧を保存します。途中で止まったコピーは自動では取り消されず、VM の ID が返らなくても何も作られていないとは限りません。容量とホストから SR へのアクセスを確認し、正確な ID を照合して、[説明のつかない残りを報告](/docs/xoa-hl/troubleshooting/)します。むやみに再試行したり、孤立して見えるディスクをまとめて削除したりしないでください。

ここで扱わないもの：実行中やサスペンド中の VM のコピー、別のプールへのコピー、テンプレートのコピー、共有ディスクやパススルーディスク、スナップショットの履歴、SR が失われた後の復旧。

## CPU とメモリを変更する {#resize-vm}

ホストの上限は保存時ではなく、VM の起動時に確認されます。D3 のホスト 1 台では、停止中の VM に 64 vCPU と 1 TiB のメモリを保存できました。その後の起動は「no hosts available」で失敗し、VM は **Halted** のままでした。編集後は必ず VM を起動して確認します。起動しなければエラーを保存し、元の値と上限・下限に戻してから再試行します。保存後の数秒間は古い値が表示される場合があります。待ってからページを再読み込みして確認します。D3 では約 4 秒後にインベントリが更新されました。

メンテナンスの時間を確保し、コンソールを開けるテスト用のゲストを使います。変更する前に、VM の ID、ゲストの状態、現在の CPU とメモリの値と上限・下限を控えます。ホストとプールの容量、ゲストの要件を確認してください。このガイドでは、CPU 数やメモリ容量の推奨値は示しません。

{{< callout type="warning" >}}
先にゲストを正常にシャットダウンし、**Halted** であることを確認します。実行中の VM を編集して、値をその場で変えられない場合、XO は再起動や強制再起動を提案することがあります。ここでは取り消し、先にシャットダウンしてください。上限を上げてもホストのリソースは予約されません。メモリを減らすと、ゲストが起動しなくなることがあります。
{{< /callout >}}

1. **詳細設定**（`/#/vms/<id>/advanced`）を開き、**CPU limits** と **Memory limits (min/max)** を控えます。CPU の行には現在値と最大値が表示されます。最大値は VM が停止しているときに変更できます。今の最大値より多くの CPU を使うには、先に最大値を上げます。
2. **一般**（`/#/vms/<id>/general`）を開きます。CPU 数をクリックし、新しい整数を入力して **Enter** を押します。待ってから更新し、値を確認してから次の変更を行います。これらの欄は、別の場所をクリックしたときにも保存されることがあります。別の場所をクリックしても、安全に取り消せるとは限りません。
3. メモリの値をクリックし、新しい量と単位を設定して **Enter** を押します。この値は設定された **動的最大値** で、ゲストが使っているメモリではありません。既存の上限・下限によって、XO は固定のメモリ設定か、動的メモリの上限・下限を更新します。
4. **一般** と **詳細設定** を更新し、変更後のすべての値を控えます。CPU 数は最大値を超えてはいけません。メモリの上限・下限は、静的最小値 ≤ 動的最小値 ≤ 動的最大値 ≤ 静的最大値 の順を保つ必要があります。XO は関連する値も調整することがあるため、クリックした項目だけが変わったと思い込まないでください。
5. テスト用 VM を起動し、コンソール、ゲスト内で見える CPU とメモリ、アプリケーションを確認します。起動しない場合や値が違う場合は、停止したままにしてタスクのエラーを保存し、同じ作業時間内に控えた設定に戻します。すべての値をもう一度確認し、原因が分かってから再試行します。

編集でエラーが出た場合は、再試行の前に実際の値を確認します。関連する変更は「すべて成功か、何も変わらないか」の 1 回の処理ではありません。拒否されても、元の値に戻ったとは限りません。[トラブルシューティング](/docs/xoa-hl/troubleshooting/)と控えたメモを手元に置いてください。

ここで扱わないもの：実行中のリソース変更（ホットプラグ）、負荷時の動的メモリ、CPU トポロジーの調整。

## テスト用 VM を削除する {#delete-vm}

D3 では、停止中のテスト VM 1 台を削除すると、その VM、スナップショット、ディスクが消え、オブジェクトは残りませんでした。別のテストでは、空のディスクを取り外しても選択した SR に残り、そのディスクを削除すると消えました。取り外しと削除は結果が異なります。共有ディスク、削除処理の失敗は未検証です。

同じ [ce47 の検証](https://github.com/Vagrantin/xcp-hl/issues/198#issuecomment-6460786269)で、保護された VM の通常の削除は拒否されて VM が残りましたが、強制削除では消えました。削除保護は誤操作を防ぐ仕組みであり、アクセス制御ではありません。保護によって削除を拒否されたら、作業を止めて理由を調べてください。強制しないでください。

{{< callout type="warning" >}}
**Remove** は VM を削除します。ディスクの切断や取り外しとは違います。このバージョンの確認画面には、ディスクを残す選択肢がありません。削除すると VM のスナップショットも消え、接続されたディスクの削除も試みられます。データやスナップショットを残す必要がある場合は、確定する前に止めて、残す方法を計画してください。この VM のスナップショットは、独立した復旧用のコピーではありません。
{{< /callout >}}

1. 対象がテスト用 VM であることを確認します。アプライアンス、元のゲスト、テンプレート、似た名前の別の VM ではないことを確かめます。ID、接続されたディスクの ID と SR、スナップショットを控えます。
2. バックアップとレプリケーションのスケジュール、他の VM がそのディスクを使っていないかを確認します。重要なデータがある場合は、先に独立した[バックアップを取り、隔離した復元を試して](/docs/xoa-hl/backup-restore/)ください。
3. ゲストを正常にシャットダウンし、**Halted** であることを確認します。削除の処理は、実行中やサスペンド中の VM を強制的に止めることがあります。**Remove** をシャットダウンの代わりに使わないでください。
4. **詳細設定** を開き、**Remove** を選びます。VM とディスクに関する警告を読み、この VM だけを確定します。続いて、保護またはブロックされた VM をそれでも削除するか確認された場合は、取り消して、保護されている理由を調べます。強制的な再試行は承認しないでください。
5. 待ってから、VM、スナップショット、SR のディスクの一覧を更新します。控えた ID と、タスクとそのエラーを確認します。別の VM にまだ接続されている共有ディスクは削除されませんが、それですべてのディスクが守られるわけではありません。スナップショットやディスクの後片付けのエラーが記録されても、削除全体は失敗にならないことがあります。VM が消えたり成功のメッセージが出たりしても、後片付けが終わったとは限りません。
6. 元の VM、他のゲスト、独立したバックアップが引き続き使えることを確認します。残ったテスト用のオブジェクトは、メモと[ディスクのガイド](/docs/xoa-hl/storage-networks/)を使って 1 つずつ確認します。孤立して見えるディスクをまとめて削除したり、容量を空けるために強制操作を繰り返したりしないでください。取り消しはできません。削除したゲストのデータは、別に試した復旧用のコピーからしか戻せません。

削除が途中で失敗した場合や、ブロックされた削除を取り消した場合は、残った VM、ディスク、スナップショットの一覧とエラーを保存します。VM が残っている場合は、権限、IP プールの予約、リソースセットの所属も確認します。XO は VM の保護を確認する前に一部の管理処理を始めるため、拒否されてもこれらの記録が変わっていないとは限りません。似た名前で VM を作り直しても、同じオブジェクトにはなりません。それ以上片付ける前に、バージョンと ID（個人情報を除く）を添えて[問題を報告](/docs/xoa-hl/troubleshooting/)してください。

## 稼働中の CPU とメモリー変更 (VM03) {#running-resources}

対象は XO 5.113.2 `e281c536`、XOA-HL ce40/ce47 のソースです。実機とゲストの確認結果は別途記録します。

1. 独立した復元確認済みバックアップ、管理者、コンソール、CPU ホットプラグとバルーンに対応する使い捨てゲストを用意します。VM UUID、現在/最大 CPU、4 つのメモリー境界、ホスト空き容量、ゲストの CPU、メモリー、アプリ状態を記録します。
2. 停止中に、例えば 1 CPU、512 MiB のゲストに最大 2 CPU、静的最大 1 GiB を確保します。**Advanced** で `静的最小 <= 動的最小 <= 動的最大 <= 静的最大` を守ります。起動して初期値を確認します。この試験で静的上限を変えるのは停止中だけです。
3. 稼働中に **General** で現在の CPU を 1 から 2 に変更します。待って両タブ、ゲストのオンライン CPU、アプリを確認します。記録した最大値を超えないでください。起動時の設定値だけでは追加成功の証拠になりません。
4. **Advanced** で動的最小 512 MiB、最大 768 MiB を静的範囲内に設定します。編集ごとに全境界を確認します。**General** のメモリーは固定構成と DMC で処理が異なるため、明示的な動的項目を使います。バルーンが落ち着いてからゲストを確認します。
5. ホストとゲストの結果を分けて記録します。元の境界と CPU 数に戻します。稼働中の削減が失敗する場合は正常停止して戻し、再起動後もアプリを確認します。

**失敗時：** エラー、メモリー不足、関連境界の予期しない変更があれば中止し、全値とタスクを読み直します。強制再起動や追加のメモリー削減で回避しないでください。

**ラボ結果、2026-11-03(一部):** ce44 のネストホストと ce40 のアプライアンスイメージ(アプリケーション 5.113.2_e281c536-47)で、ゲストツールのない使い捨てゲストに対し、アプライアンスの JSON-RPC API 経由で観察しました。最大値を超えるライブ CPU 変更は拒否されました(`VM state is running but should be halted`)。ホットプラグ非対応のゲストでの CPU ホット変更は `VM lacks feature` で失敗し、起動時の数は次の変更まで新しい値のまま、オンラインの数は 1 のままでした。両方を読み戻してください。ホストの CPU 数を超える最大値は起動を妨げます(`Not enough CPUs`)。動的メモリの境界は実行中に変更できました。静的最大値は実行中に変更できず、`memory` は動的最大値だけを変更します。ゲスト内の CPU とバルーンの反応は観察していないため、このモードは未完了のままです。

## 稼働中または中断中の VM のコピー (VM07) {#active-copy}

同じ XO5/ce40/ce47 が対象です。[フルコピー](#full-copy)に次の確認を追加します。

1. 通常ディスク、同期済みサンプルとチェックサム、同一プールの書き込み可能 SR の空き容量を用意します。使い捨てゲストから起動前に全 VIF を削除し、ジョブを無効化して既存スナップショットを記録します。
2. **Running** でデータを同期し、**Copy → Full copy**、一意の名前、正確な SR を指定します。同一プールでは圧縮を使用しません。バックエンドは一時スナップショットをコピーして削除を試みます。アプリ静止や RAM 保存ではありません。
3. **Suspended** は別に試験します。隔離したソースを中断し、状態を確認して別名でフルコピーします。このリリースでは拒否されます(下のラボ結果を参照)。コピーが中断メモリーや電源状態を引き継ぐとは仮定しません。
4. ソース/コピーの UUID、VDI、SR、電源状態、一時スナップショット残存を記録します。コピーを停止状態に保ち、起動/再開前に全 VIF を削除します。停止していなければ先に調査します。コンソールでサンプルのチェックサムとソースの正常状態を確認します。

**失敗時：** 再試行や削除前に部分的な VM、ディスク、スナップショットを調べます。ソースと独立バックアップを保持します。タスク成功だけでは整合性や履歴維持を証明できません。

**ラボ結果、2026-11-03(一部):** API 経由で、実行中のソースから独自のディスクと新しい MAC アドレスを持つ停止状態のコピーができました。ソースは実行中のままで、一時スナップショットは残りませんでした。コピーはソースの VIF を引き継ぐため、起動前に削除してください。一時停止中のソースは拒否されます(`VM state is suspended but should be halted`)。先に再開または停止し、一時停止状態のコピーは期待しないでください。コピーの起動とチェックサムは実行していないため、このモードは未完了のままです。

## 稼働中とメモリー付きスナップショット (VM09) {#active-snapshots}

同じ XO5/ce40/ce47 が対象です。VIF のない使い捨てゲスト、通常の対象ディスク、コンソール、ホスト/SR の空き容量を用意し、ジョブを無効化します。UUID、対象ディスク、初期チェックサム、既存ポイントを記録します。

1. 稼働中に `live-A` をファイルに書いて同期し、**Snapshots → New snapshot** を選択します。UUID とディスク対象を確認します。ディスクのポイントでありアプリ整合性の保証ではありません。
2. `live-B` に変更して同期し、正常停止して[復元手順](#snapshot-revert)を使います。**Snapshot before** は有効のままです。稼働中ポイントへの復元で自動起動する可能性があるため、保存時点から隔離が必要です。状態、VIF、コンソール、`live-A` のチェックサムを確認します。
3. 別の試験で、ゲストのエディターに無害な未保存の目印を残し、**New snapshot with memory** を選びます。UUID と実際のメモリー保存を確認します。`VM_BAD_POWER_STATE` ではディスクのみへフォールバックするためボタンだけで判断しません。
4. 目印とファイルを変更後、十分な容量と事前ポイントを用意してその checkpoint に戻します。RAM の目印、ディスクのチェックサム、コンソール、アプリ、電源状態を確認します。ディスクのみの成功をメモリー成功としません。
5. 確認後、記録した試験ポイントだけを削除し、残存ディスク、ポイント、容量を確認します。バックアップ管理のポイントには触れません。

**失敗時：** エラーと一覧を保存し、再試行前にソースの状態を確認します。除外/共有ディスク、パススルー、アプリ静止は別途検証が必要です。

**ラボ結果、2026-11-03(一部):** 実行中のゲストで、ディスクスナップショットの電源状態は Halted で suspend VDI はありませんでした。**メモリ付き新規スナップショット**は、電源状態 Suspended で suspend VDI を持つスナップショットになりました。どちらに戻しても VM は Running のままでした。検証用ゲストにはゲストツールがないため、RAM マーカーとゲストデータは確認しておらず、このモードは未完了のままです。

## 削除時に選択したディスクを保持 (VM11) {#retain-disks}

同じ XO5/ce40/ce47 が対象です。`deleteDisks` は VM 全体の真偽値で、ディスク一覧ではありません。停止した使い捨て VM で、保持する VBD を先に外します。

1. 独立した復元用コピーを確認します。VM UUID、全 VBD/VDI、SR、サイズ、スナップショット、保持対象を記録します。関連ジョブを止め、通常の非共有ディスクを使います。
2. **Disks** で**仮想ディスクをこの VM から取り外す** を使い、**仮想ディスクを破棄** を選びません。行の操作は VBD を即時削除します。VM 削除にはディスクごとの保持チェック欄がありません。再読み込み後、VBD がなく、正確な VDI が SR に残ることを確認します。単なる切断では不十分です。
3. 停止した対象 VM を通常の確認で削除します。スナップショットと残った対象ディスクも削除され得ます。強制要求は取り消して調査します。
4. VM の消失、保持 VDI の存在、意図したディスクだけの削除を確認します。保持 VDI を別の停止中の隔離復元 VM に接続し、起動してチェックサムを確認後、データを削除せず外します。

**失敗時：** 接続解除とデータ削除を区別できない場合は中止します。エラー後は部分的な VM/VDI/ポイントを記録します。VM 行の消失やディスク切断から保持成功を推測しません。
