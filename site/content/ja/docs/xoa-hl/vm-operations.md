## VM のコンソールを開いて確認する {#vm-console}

**XOA-HL アプライアンスのアドレスを開いたブラウザー**、管理者アカウントと、ゲストの画面を表示できる特定済みの使い捨て VM を使います。接続前に UUID、実行ホストと想定するゲストを記録してください。コンソールには VM の**操作権限**が必要で、Viewer 権限だけでは不十分です。この VNC コンソールにゲスト IP は不要です。テスト VM のネットワーク隔離は保持し、ブラウザーからアプライアンス、アプライアンスからホストへの接続を確認します。以下は上記 ce38 のソース確認済みプレビューであり、実機のコンソール・キーボード・クリップボード受け入れ確認は保留中です。

1. 対象 VM の **コンソール** (`/#/vms/<id>/console`) を開き、対象と **Running** を確認します。この版は、一時停止・サスペンドを含む他の状態では英語の **Console is only available for running VMs.** を表示します。起動・再開には別途計画した[電源操作](#1-起動停止再起動)を使い、コンソール表示のために強制再起動しないでください。
2. 想定するゲスト画面を待ちます。入力前にゲストのログイン・インストーラー・既知のアプリケーションを識別してください。認証情報はゲスト用であり、XOA-HL やホスト用ではありません。ポインターをコンソールの描画領域に入れるとキーボード・マウス入力を取得し、外へ出すと解放して XO のショートカットを戻します。使い捨てゲストのエディターで `console-test` など無害な文字列だけを入力し、削除します。シェルのコマンドやパスワード欄では試さないでください。画面が見えるだけでは入力成功を証明しません。
3. 大きなデスクトップでは表示倍率の初期値が **100%** で、ゲストの設定解像度ではなくブラウザー内の表示を変更します。小さい画面では操作欄が表示されない場合があります。**Hide infos / Show infos** は XO の情報・ヘッダーの表示切り替えであり、ゲストの停止やブラウザーの全画面操作ではありません。倍率を変えたら、画面とポインターの位置が使用できることを確認します。
4. 終了時は別の画面に移動し、VM・ホスト ID、電源状態と、表示・無害な入力・ポインター解放の結果を記録します。タブを離れると、このブラウザーのコンソール接続を閉じますが、ゲストは停止しません。セッション中に VM が再起動した場合は、コンソールを開き直して新しい画面を確認します。ソースには再起動時の切断検出の制限が記録されており、自動再接続の試行だけではゲストの正常性を証明しません。

**確認：** 正しい実行中ゲストが見え、無害な入力が届き、ポインターを外へ出すと XO の操作に戻れ、VM は意図した状態を保持します。

### クリップボードとリモートクライアントの操作

- クリップボードのテキスト欄は、編集後の短い待ち時間を経てリモートのクリップボードに送信します。**コピー** は現在の文字列をブラウザーのローカルクリップボードへコピーします。複数行のボタンは **クリップボードに送信** を開きます。無害な文字列を使い、ゲストへの貼り付けは個別に確認してください。欄の変更だけではゲストの対応を証明しません。テストや画面キャプチャにパスワード・私的データを含めないでください。
- **SSH**、**SSH as…** と **RDP** は別のショートカットです。ゲストが報告する主 IP を使い、利用者のコンピューターで `ssh://` または `rdp://` のハンドラーを起動します。IP の報告でボタンが有効になりますが、ローカルクライアント、ゲストのサービス、認証情報やネットワーク接続の存在は保証しません。VNC の修復・置き換え操作ではありません。
- **Ctrl+Alt+Del** は確認画面を開き、確定するとゲストにキーを送ります。効果はゲストによって異なり、中断を招く場合があります。この練習では取り消し、接続テストには使いません。ISO 選択欄もマウントするゲストのメディアを変更するため、操作前に[インストール・メディアの手順](/docs/xoa-hl/create-vm/)を確認します。

フランス語の表示は **Console**、**Copier**、**Ctrl+Alt+Supp** と **Cacher les infos / Afficher les infos** です。日本語は **コンソール**、**コピー**、**Ctrl+Alt+Del** と **クリップボードに送信** を使い、ヘッダーのツールチップは **Hide infos / Show infos** のままです。この版の他の未翻訳操作は英語にフォールバックする場合があります。

### 空白・利用不可・応答しないコンソールを調べる

1. **Running 以外、または無効：** まず状態とメッセージを読みます。Running でも `disable_pv_vnc=1` なら描画領域の代わりに **Console is disabled for this VM** 相当の表示になります。日本語の **このVMのコンソールを無効化します** は、その無効状態を示す情報であり、有効にするボタンではありません。方針を記録し、VM 設定を変更する前に管理者へ確認してください。再起動やゲストツールの導入で有効になるとは判断しません。
2. **接続できない、切断を繰り返す：** VM の操作権限とホスト接続を確認します。ブラウザーの開発者ツールで `/api/consoles/<id>` に終わる WebSocket リクエストを調べ、表示されたエラー・状態を記録します。リバースプロキシは通常ページの要求だけでなく、このアップグレードを通す必要があります。ブラウザーからアプライアンスへの TLS・アクセスと、アプライアンスからホストへの経路を分けて確認します。ゲスト IP、SSH サーバー、ゲストのファイアウォールは VNC プロキシの経路ではありません。特定した経路・信頼の問題を担当者と修正し、一般的な対処として VNC ポートを公開したり、証明書検証を無効にしたりしないでください。
3. **接続するが画面が空白・古い：** 対象 VM、想定する起動・表示と直近の電源操作を確認します。再起動後はタブを開き直し、利用できる場合は別の認可済み観測と比較します。同じ症状がゲストの画面・起動、または接続に起因する場合があるため、ゲスト固有の対処前に証拠を保存します。描画領域が黒いというだけで電源操作を繰り返し、再インストールや起動メディア変更を行わないでください。
4. **画面は見えるが入力・貼り付けができない：** ポインターを領域へ入れて外へ出し、エディターの無害な入力テストを繰り返します。ブラウザー・OS によるキーの取得と、ゲストが目的のクリップボード操作に対応するかを確認します。SSH・RDP の失敗は別に扱います。[問題報告](/docs/xoa-hl/troubleshooting/#問題を報告する)にブラウザー・版、VM・ホスト ID、日時、電源状態、正確な表示と秘密情報を除いた接続エラーを記載します。Cookie、トークン、クリップボードやゲスト画面の内容を含む可能性があるため、生のブラウザートレースは公開しないでください。

XO `e281c536` のコンソールの根拠：[タブ・操作](https://github.com/vatesfr/xen-orchestra/blob/e281c536d3b1e97ccfb3b0826f91b7dbb6c4478c/packages/xo-web/src/xo-app/vm/tab-console.js)、[入力取得・倍率・再接続](https://github.com/vatesfr/xen-orchestra/blob/e281c536d3b1e97ccfb3b0826f91b7dbb6c4478c/packages/xo-web/src/common/react-novnc.js)、[認証・操作権限の確認](https://github.com/vatesfr/xen-orchestra/blob/e281c536d3b1e97ccfb3b0826f91b7dbb6c4478c/packages/xo-server/src/index.mjs)、[ホストのコンソールへのプロキシ](https://github.com/vatesfr/xen-orchestra/blob/e281c536d3b1e97ccfb3b0826f91b7dbb6c4478c/packages/xo-server/src/proxy-console.mjs)。

## 1. 起動、停止、再起動

対象 VM を開きます (`/#/vms/<id>/general`)。停止中なら **Start** を選び、状態とコンソールでゲストの起動を確認します。実行中の **Stop** と **Reboot** は、最初にゲストの正常なシャットダウンまたは再起動を要求します。

ゲスト側の機能が不足している場合や操作がブロックされている場合、XO は強制操作またはブロックの回避を確認することがあります。続行する前にメッセージを読んでください。強制停止や強制再起動ではゲストのデータを失う可能性があります。可能ならゲスト内でシャットダウンします。タスク実行中に繰り返しクリックしないでください。完了後に VM の状態とコンソールを確認します。成功通知だけではアプリケーションの正常動作を確認できません。

## 2. 保護方法を選ぶ

| 種類 | 目的と制限 |
| --- | --- |
| スナップショット | VM のある時点の状態。元のストレージに依存し、独立したバックアップではない |
| 高速クローン | ストレージ効率のよいコピーを使う別の VM。同じストレージの喪失には備えられない |
| フルコピー | 選択した SR にディスク VDI をコピーした別の VM。使用前にデータ、配置と隔離を確認する |
| バックアップ | 別に保存する復旧用コピー。隔離した復元で確認する |

VM の変更に伴い、スナップショットとクローンもストレージを消費します。SR の空き容量を確認し、削除するのは確実に識別したテスト用オブジェクトだけにしてください。稼働中のスナップショットはアプリケーションの整合性を保証しません。

## 3. 停止中のスナップショットを作成する <span class="hx:absolute" id="3-停止中のスナップショットを作成する"></span> {#stopped-snapshot}

このブラウザーでの練習には、XOA-HL 管理者アカウントと、通常のディスクを持つ使い捨て VM 1 台、利用できるコンソールが必要です。共有ディスクやパススルーデバイスは含めません。バックアップ・レプリケーションの開始条件を無効にし、実行中のタスクが終わるまで待ちます。保持する必要があるデータは、独立した復旧用コピーを用意してください。稼働中・メモリ付きスナップショットやアプリケーション整合性の保証は、この練習の対象外です。

1. ゲストで `snapshot-A` を含む重要でないファイルを作り、チェックサムを記録します。正常にシャットダウンして **Halted** を確認します。VM の UUID、ディスク VDI の ID・SR・サイズ、既存スナップショットの UUID と SR の空き容量を記録します。取得前に[テスト VM のネットワークインターフェースをすべて削除](/docs/xoa-hl/storage-networks/)して、VIF 一覧が空であることを確認し、以降はコンソールで操作します。
2. 各ディスクの名前を確認します。このソースは、名前に文字列 `[NOSNAP]` を含む VDI を除外する場合があります。これはディスク名の一部であり、VM のタグではありません。除外・共有・パススルーディスクには別の手順が必要です。既存の方針を回避するために名前を変更しないでください。この練習ではマーカーのない通常のディスクを使い、スナップショット、取得後の書き込みと復元前のスナップショットに必要な容量を確保します。
3. **スナップショット** (`/#/vms/<id>/snapshots`) で **New snapshot** を一度だけ選びます。この VM 個別のボタンは、先に名前を尋ねず、そのまま作成します。初期名は VM 名と ISO 形式の日時の組み合わせです。**New snapshot with memory** は使用しません。この版ではこれらの操作名は英語です。
4. 完了を待ち、一覧を更新し、**Creation date** と行の UUID コピー操作で新しい行を特定します。異なる UUID を記録してください。名前や日時だけでは不十分です。**Name** を `lab-snapshot-A` に変更し、説明欄に明確なテストメモを入力して、更新後に両方を読み戻します。この版の日本語 UI では説明欄の見出しも **Name** になっているため、列の位置と内容を照合してください。スナップショットのディスク一覧と SR を記録した状態と比較し、タスクのエラーと空き容量を確認します。スナップショットの VDI ID が元ディスクと異なるのは想定されるため、元 ID との一致ではなくディスクの範囲とサイズを確認します。

**確認：** 特定した停止中のスナップショットが対象の通常ディスクを含み、元 VM は停止中で VIF がありません。作成や名前変更に失敗したら、エラーと実際の VM・スナップショット・ディスク一覧を保存してから再試行します。ID が返らない、通知がないというだけでは未作成と判断できません。名前変更の失敗は作成を取り消しません。

## 4. テスト VM をスナップショットに戻す <span class="hx:absolute" id="4-テスト-vm-をスナップショットに戻す"></span> {#snapshot-revert}

{{< callout type="warning" >}}
復元は VM の現在の状態を置き換え、以前のネットワークインターフェースを含む設定が戻る場合があります。取得後の変更は失われる可能性があります。この隔離した使い捨て VM だけを使い、復元前に停止し、起動前に VIF を再確認してください。同じ SR 上のスナップショットは SR 喪失から保護しません。
{{< /callout >}}

1. 隔離した VM を起動し、ファイルを `snapshot-B` に変更して新しいチェックサムを記録します。正常にシャットダウンして **Halted** を確認し、現在のディスク・VIF・スナップショット一覧を記録します。選択する UUID がセクション 3 の `lab-snapshot-A` であり、バックアップ管理のスナップショットや別 VM の復元点でないことを確認します。
2. **スナップショット** で対象行の **Revert VM to this snapshot** を選び、**Revert your VM** の確認画面を読みます。この練習では **Snapshot before** を有効のままにし、先に容量を確認します。初期状態で有効なこの選択肢は、復元要求の前に現在の状態を別の通常スナップショットとして保存します。独立したバックアップや、ロールバックを保証する一括処理ではありません。対象、隔離、容量が不確かな場合は取り消します。
3. 一度だけ確定し、完了を待ちます。更新後に対象 UUID、新しい復元前スナップショットの UUID、電源状態、ディスク、VIF とエラーを記録します。この UI 経路では事前スナップショットの失敗で次の復元要求が実行されません。後の復元が失敗した場合は、事前スナップショットが残る可能性があります。再試行前に実際の状態を確認し、原因不明のエラーを回避するために保存を無効にしないでください。
4. 手動起動前に **Halted** と空の VIF 一覧を確認します。VIF が戻っていたら停止中に削除し、隔離を読み戻します。稼働中に取得したスナップショットは、復元後に非同期の起動・再開を引き起こす場合があります。復元の成功はゲスト起動の成功を証明しません。そのようなスナップショットは、この練習の対象外です。
5. コンソールで起動し、`snapshot-A` と元のチェックサム、ゲストのディスクとアプリケーションを確認します。再度シャットダウンして結果を記録します。追加の事前スナップショットは `snapshot-B` の状態として別途特定してください。その復旧には個別の管理された検証が必要であり、当然の取り消し操作とは扱いません。

### 特定したテストスナップショットを削除する {#snapshot-cleanup}

結果を記録し、必要な独立した復旧用コピーを用意してから、VM を停止したまま、UUID と所属を記録したテストスナップショットだけを削除します。**スナップショット** の対象行で **Remove this snapshot** を選び、**Delete snapshot** を読んで 1 件だけ確定します。**Remove selected snapshots** による一括削除やバックアップ管理の復元点の削除は行わず、VM の **Remove** と混同しないでください。

完了を待ち、スナップショット、VM ディスクと SR 容量を更新します。記録した UUID が消え、保持する復元点と元 VM が残っていること、エラーを確認してください。ディスクの後片付けの失敗は、削除全体を失敗にせずログに記録される場合があります。行の消失や成功通知だけでは完全な削除や即時の空き容量回復を証明しません。残存 ID を保存して[不明なオブジェクトを報告](/docs/xoa-hl/troubleshooting/)し、孤立して見える VDI を一括削除しないでください。この手順には削除の取り消しはありません。

## 5. 隔離した高速クローンを準備する

停止中の使い捨て VM で **Fast clone** を選びます。新しい VM（初期名の末尾は `_clone`）を探し、異なる識別情報を記録して名前を変更します。[継承したネットワークインターフェースをすべて削除する](/docs/xoa-hl/storage-networks/)か、外部の隔離を確認するまでは停止状態を保ちます。MAC アドレスの自動生成だけでは、コピーされた IP アドレス、資格情報、アプリケーションの識別情報は変わりません。

その後クローンを起動してコンソールを確認します。重複した識別情報を解消し、隔離を確認してからネットワークを再接続してください。エラー後にクローンが見つからなければ、再試行前に一覧とタスクを確認します。この練習ではライブマイグレーション、メモリを含むスナップショット、SR 喪失後の復旧を検証しません。

### 同じプール内でフルコピーを作成する {#full-copy}

選択した SR に通常のディスクコピーを作る場合は、個別の **Fast clone** ではなく **仮想マシンの複製** を使います。コピー画面にも **Fast clone** があるため、この練習では **Full copy** を選択したままにします。画面名 **Copy VM**、**Name**、**Select SR** とコピー方式は、この版では英語表示です。高速クローンも同じプール内のフルコピーも、独立したバックアップや検証済みの災害復旧を確立するものではありません。

1. 通常のディスクを接続した使い捨て VM 1 台を使い、共有ディスクやパススルーデバイスは含めません。ゲストを操作できる間に、重要でないファイルとチェックサムを記録します。正常にシャットダウンして **Halted** を確認し、元 VM の ID、ディスク VDI の ID・SR・サイズ、VIF と既存のスナップショットを記録します。この練習は現在の VM のディスクを確認するもので、スナップショット履歴のコピーは保証しません。
2. **同じプールにある別の書き込み可能な VM ディスク用 SR** を特定します。ID、空き容量と、コピーを実行する予定のホストからのアクセスを確認します。ISO ライブラリはこのコピー先ではありません。ディスクのコピーと今後の増加に必要な容量を確保します。画面は容量を予約せず、十分な空きを証明するものでもありません。コピー先が利用できない場合は、コピーを開始せずにストレージへのアクセスを解決します。
3. 元 VM で **仮想マシンの複製** を選びます。**Copy VM** の **Name** に `lab-vm-full-copy` など一意のテスト名を入力します。初期値のパターンは `{name}_COPY` で、空欄なら元の名前を保持します。**Full copy** を確認し、**Select SR** で記録した ID とプールを照合します。似た名前だけで選ばないでください。実際の UI プランによっては別のプールも表示されます。それを選ぶとサーバー側はエクスポート・インポート経路になり、この練習の対象外です。**圧縮** は **Disabled** のままにします。同じプール内では、圧縮転送ではなく XAPI `VM.copy` を使用します。
4. 一度だけ確定してタスクを待ちます。一覧を更新し、異なる ID と指定した名前で新しい VM を特定します。**Halted**、ディスクの数・サイズ、新しい VDI ID と各ディスクのコピー先 SR を確認します。元 VM と元ディスクが変更されずに残っていることも確認してください。通知や同じ名前だけではコピーの完了を証明できません。新しい VM が予期せず実行中になっている場合やオブジェクトが想定と異なる場合は、練習を中止して隔離を回復してから進めます。
5. 新しい VM を停止したまま、[継承された VIF をすべて削除](/docs/xoa-hl/storage-networks/)します。初回起動前に VIF 一覧が空であることを再確認してください。MAC の再生成には依存しません。ゲストの IP アドレス、認証情報とアプリケーションの識別情報はコピーされます。隔離したコピーだけを起動し、コンソールで記録したファイルのチェックサム、ゲストのディスクとアプリケーションの動作を確認します。ネットワークを再接続する前に重複する識別情報を解消し、その確認中は元 VM を隔離または停止したままにします。
6. 確認後にコピーをシャットダウンします。結果を記録し、セクション 7 に従って特定済みのテスト VM とディスクだけを削除します。元 VM と独立したバックアップは保持します。後片付けは破壊的操作であり、操作後の一覧確認が別途必要です。

エラー、接続切断やリクエスト中断が起きたら、再試行前にタスク・エラーと、コピー元・コピー先の VM、VDI、スナップショット一覧を保存します。ソースのラッパーは、不完全な XAPI コピーのロールバックを保証しません。VM ID が返らなかっただけで、何も作成されていないとは判断できません。容量とホスト・SR へのアクセスを確認し、正確な ID を照合して、[説明できない残存オブジェクトを報告](/docs/xoa-hl/troubleshooting/)します。無条件に再試行したり、孤立したように見えるディスクを一括削除したりしないでください。実行中・サスペンド中のコピー、プール間転送、テンプレートのコピー、共有・パススルーディスク、スナップショット履歴の保持と SR 喪失後の復旧には、個別の受け入れ確認が必要です。

## 6. 停止中の VM のリソースを変更する

メンテナンス時間を確保し、コンソールにアクセスできる使い捨てのゲストを使用します。変更前に ID、ゲストの状態、現在の CPU・メモリ値と上限・下限を記録してください。ホスト・プールの容量とゲストの要件を確認します。このガイドでは、すべての環境に共通する CPU 数やメモリ容量を指定しません。

{{< callout type="warning" >}}
この練習ではゲストを正常にシャットダウンし、**Halted** を確認してから変更します。実行中に変更できない値を編集すると、再起動または強制再起動を提案する場合があります。ここではその確認をキャンセルし、先に停止してください。上限を増やしてもホストのリソースが確保されるとは限りません。メモリを減らすとゲストが起動できなくなる場合があります。
{{< /callout >}}

1. **詳細設定** (`/#/vms/<id>/advanced`) を開き、**CPU limits** と **Memory limits (min/max)** を記録します。この固定バージョンの日本語カタログでは、この二つのラベルは英語です。CPU の行は現在値／最大値を示し、VM が実行中でなければ最大値を編集できます。予定する CPU 数が記録した最大値を超える場合は、VM を停止した状態で先に最大値を増やします。
2. **一般** (`/#/vms/<id>/general`) を開きます。CPU 数をクリックし、予定する正の整数を入力して **Enter** を押します。完了を待って再読み込みし、値を確認してから次の変更を行います。インライン入力はフォーカスを失う際にも保存される場合があります。別の場所をクリックしても、安全に編集をキャンセルできるとは限りません。
3. メモリ値をクリックし、容量・単位の入力で予定する値を設定して **Enter** を押します。表示値は設定された**動的最大値**であり、ゲスト内で現在使用している RAM の測定値ではありません。既存の範囲に応じて、バックエンドは固定メモリ構成または動的メモリの制限を変更します。
4. **一般**と**詳細設定**を再読み込みし、変更後のすべての値を記録します。CPU 数は最大値以下にします。メモリの範囲は、静的最小値 ≤ 動的最小値 ≤ 動的最大値 ≤ 静的最大値の順序を保つ必要があります。ソースでは関連する制限も調整される場合があるため、クリックした項目だけが変わったとは判断しないでください。この練習は、ホットプラグ、負荷時の動的メモリ、CPU トポロジーの調整を検証するものではありません。
5. テスト VM を起動し、コンソール、ゲストから見える CPU・メモリ、アプリケーションの状態を確認します。起動できない場合や値が想定と異なる場合は停止状態に保ち、タスクのエラーを保存して、同じ管理された作業時間内で記録した構成に戻します。すべての制限を確認し、原因を特定してから再試行してください。成功通知だけでは十分ではありません。

編集でエラーが出た場合は、再試行前に実際の値を確認します。関連する変更はアトミックなトランザクションとして保証されず、拒否されたからといってすべての値が元に戻ったとは限りません。[トラブルシューティング](/docs/xoa-hl/troubleshooting/)と記録した変更前の状態を用意してください。

## 7. 使い捨ての VM だけを削除する

{{< callout type="warning" >}}
**Remove** は VM に対する破壊的な操作であり、ディスクの切断や取り外しとは異なります。この固定バージョンの通常の確認画面には、ディスクを保持する選択肢はありません。削除では VM のスナップショットも処理され、接続されたディスクの VDI の削除が試みられます。データやスナップショットを残す必要がある場合は、確認する前に作業を止め、別の保存手順を計画してください。この VM のスナップショットは独立した復旧用コピーではありません。
{{< /callout >}}

1. 対象が使い捨て VM であり、アプライアンス、元のゲスト、テンプレート、似た名前の別の VM ではないことを確認します。ID、接続されたディスクの ID・SR、スナップショットを記録します。削除前にバックアップ・レプリケーションのスケジュールと、共有ディスクを使用する他の VM を確認してください。重要なデータについては、先に独立した[バックアップと隔離した復元テスト](/docs/xoa-hl/backup-restore/)を完了します。
2. ゲストを正常にシャットダウンし、**Halted** を確認します。削除のバックエンドは実行中やサスペンド中の VM を強制停止する場合があります。**Remove** を正常なシャットダウンの代わりに使わないでください。
3. **詳細設定**を開き、**Remove** を選びます。VM とディスクの警告を読み、予定した対象だけを確認します。保護やブロックを無視して削除する二回目の確認が出た場合は、この練習を中止し、強制再試行を承認する代わりに保護の理由を調べてください。
4. 完了を待ち、VM、スナップショット、SR のディスク一覧を再読み込みします。記録した ID と削除タスク・エラーを確認してください。このソースの処理では、別の非コントロールドメイン VM にまだ接続されている共有 VDI は削除をスキップします。この例外はすべてのディスクを保持する保証ではありません。スナップショットや VDI の後処理エラーは、削除全体を失敗にせずログに記録される場合があります。VM が一覧から消えたり成功通知が出たりしても、後処理がすべて完了したとは判断できません。
5. 元の VM、他のゲスト、必要な独立したバックアップが引き続き利用できることを確認します。[ディスク管理の操作の違い](/docs/xoa-hl/storage-networks/)と記録した ID を使い、残ったテスト用オブジェクトを一つずつ確認してください。孤立して見えるディスクを一括削除したり、空き容量を戻すために強制操作を再試行したりしないでください。このガイドでは削除を取り消せません。削除したゲストデータの復旧には、別に検証した復旧用コピーが必要です。

途中で削除が失敗した場合や、ブロック後の確認をキャンセルした場合は、残った VM・ディスク・スナップショット一覧とエラーを保存します。VM が残っている場合は、権限、IP プールの予約、リソースセットへの所属も確認してください。API はバックエンドの削除保護の確認より前に一部の管理処理を開始するため、拒否されてもこれらの記録が変わっていないとは限りません。同じような名前で VM を作り直しても、同じオブジェクトにはなりません。追加の削除を行う前に、バージョンと機密情報を除いた ID を添えて[問題を報告](/docs/xoa-hl/troubleshooting/)してください。
