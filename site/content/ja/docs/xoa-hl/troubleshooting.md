## 次の確認を選ぶ

| 症状 | 確認と次の操作 | 続ける前の確認 |
| --- | --- | --- |
| アプライアンスのページが開かない | XO Lite で VM が動作中か、アドレスとネットワークが正しいか確認。コンソールから以下の `xo-server` とディスク容量を調べる | 正しい URL でログイン画面が開く |
| 初回ログインの認証情報で入れない | [初回ログイン](/docs/xoa-hl/first-login/)の Web 認証情報と代替アカウントを確認。許可されたコンソールから初期設定ログを調べる | ログインでき、初期パスワードを変更済み |
| ホストが有効でもインベントリが空 | Settings → Servers でエラーを読み、アドレス、認証情報、証明書の識別、アプライアンスからの接続を確認 | 対象ホストとストレージがエラーなく表示される |
| VM の作成やインストールが失敗 | [VM 手順](/docs/xoa-hl/create-vm/)とプール、テンプレート、SR 容量、ネットワーク、起動メディアを照合。再試行前にタスクのエラーを記録 | 使い捨て VM が目的のインストーラーを起動する |
| バックアップや復元が失敗 | ジョブログを読み、リモート先、認証情報、容量、対象 SR を確認。[バックアップ手順](/docs/xoa-hl/backup-restore/)を参照し、復元した NIC は初回起動前にすべて削除する | ジョブが成功し、隔離した復元ゲストに期待するデータがある |
| 更新画面が切断 | 管理されたインストールのログとサービス状態を確認。RPM は `xo-server` を再起動する。重複する処理を開始しない | 成功マーカー、期待するバージョン、ログイン、ホスト一覧を確認 |
| 更新確認が ERROR | `/run/xoa-hl/status` と確認サービスのログを読む。再確認前にリポジトリ・ネットワークのエラーや実行中の更新を調べる | 新しい結果が `UP_TO_DATE` または `AVAILABLE` |
| 自動更新が実行されない | 保存したモード、アプライアンスのタイムゾーン、遅延、タイマーを確認。停止中に逃した実行時間帯は起動時に再実行されない | 目的のタイマーが予定され、後の実行記録が時間帯と一致する |
| 設定インポートが失敗 | エラーとサーバーログを保存。一部の変更が残る可能性がある。[隔離したインポート](/docs/xoa-hl/configuration-backup/)を参照 | 新しい使い捨て環境でテストに合格する。失敗した対象が元の状態とは考えない |

コンソールの操作や空白・応答しない画面には、[VM コンソールの確認手順](/docs/xoa-hl/vm-operations/#vm-console)を使います。

## ネットワーク接続を診断する {#network-connectivity}

既存の通常のゲストネットワーク、または[検証用 VLAN](/docs/xoa-hl/storage-networks/#host-vlan-network) を読み取り専用で調査します。VM・プール・ホストの全体を確認できる XOA-HL 管理者としてサインインしてください。ゲスト内の確認には許可されたコンソールセッションが必要です。スイッチ、DNS、ファイアウォールは各管理者が確認します。独立したホストコンソールへのアクセスを確保してください。この手順のために障害を発生させたり、管理ネットワークを変更したりしないでください。ボンド、SDN、ゲストの VLAN トランク、緊急のネットワーク復旧には別の手順が必要です。

### 1. 失敗している経路を特定する

タイムゾーン付きの時刻、最後に成功した操作、正確なエラー、送信元マシン、宛先名・アドレス、プロトコル、サービスのポートを記録します。再試行前に初期状態を保存してください。手元の PC から成功しても、アプライアンス、ホスト、ゲストからの接続を確認したことにはなりません。

| 経路 | 確認する場所 |
| --- | --- |
| ブラウザー → アプライアンス | クライアントで URL、名前解決、証明書の識別情報を確認します。ページに接続できなければ許可されたアプライアンスのコンソールから、後述のサービス確認を行います。 |
| アプライアンス → ホスト | `/#/settings/servers` の接続エラーを読み、[ホスト接続の手順](/docs/xoa-hl/hosts-pools/) に進みます。有効という設定だけでは接続成功を意味しません。 |
| ホスト → NFS SR | [ストレージの確認](/docs/xoa-hl/storage-networks/#nfs-vm-storage) で SR と、そのホストの接続・保存先を確認します。ゲストやアプライアンスからのテストはホストからのアクセス確認の代わりにはなりません。 |
| アプライアンス → バックアップ先 | [バックアップ障害の確認](#backup-failures) に進みます。NFS SR とバックアップ先では、アクセス元と識別情報が異なります。 |
| ゲスト → 相手・サービス | 以下でインターフェースの対応とゲストを確認します。XO へのログインやコンソール表示の成功は、ゲストのネットワーク接続を証明しません。 |

### 2. ゲストのインターフェースからホストの物理接続までたどる

1. VM UUID、電源状態、実行ホスト、プールを記録し、VM のネットワークタブ (`/#/vms/<id>/network`) を開きます。VIF 行の UUID コピー機能を使い、デバイス番号、MAC、ネットワーク、MTU、状態を記録します。プール画面 (`/#/pools/<id>/network`) で名前だけでなく正確なネットワーク UUID を照合してください。編集可能なネットワーク・MAC 欄や接続ボタンを押さずに読み取ります。
2. **Connected** は VIF の接続状態を表します。停止中の VM で VIF が未接続でも、それだけでは障害ではありません。**IP addresses** はゲストメトリクスを VIF デバイス別に表示したものです。表示がなくてもゲスト設定がないとは限らず、表示された IP も現在の到達性テストではありません。ゲストコンソールと[ゲストエージェントの確認](/docs/xoa-hl/guest-tools/) を照合します。
3. ロックモードの表示と **Allowed IPs** は、報告された IP と分けて記録します。これらは通信ポリシーの設定であり、ゲストに IP を割り当てる入力欄ではありません。警告を保存し、適用されるポリシーをネットワーク管理者に確認してください。診断の近道としてロック解除、制限の削除、MAC・MTU の変更、セキュリティの無効化を行わないでください。
4. プールのネットワーク行で **PIFs** を展開し、実行ホストを探します。VLAN の概要はマスターを基準にしています。実際のホストのネットワークタブ (`/#/hosts/<id>/network`) で PIF UUID、デバイス・MAC、ネットワーク、VLAN、MTU、管理フラグ、IP モードを確認し、承認済みの配線・スイッチ構成と照合します。意図的な内部ネットワークには物理接続がない場合があります。障害と判断する前に想定構成を確認してください。
5. 接続状態とキャリアを分けて確認します。ホストの **Connected** ボタンは PIF の接続状態を示します。別の物理リンクアイコンと、プールで展開した PIF の状態はキャリアを使います。このソースでは PIF メトリクスがない場合もキャリアが false になり得るため、否定的な表示だけでケーブルの抜けとは断定できません。更新してホスト・スイッチの観測と照合します。経路を調べるために PIF の切り替え、VLAN・MTU・IP の編集、ネットワーク削除、ネットワーク再起動を行わないでください。

### 3. ゲスト設定とサービスの結果を比較する

**ゲストコンソール**で MAC によりインターフェースを特定し、その OS のツールで現在のアドレス・プレフィックス、経路、DNS 設定を確認します。ゲストのインターフェース名がホストのデバイス名と一致するとは限りません。管理者が承認した重複しないアドレスとサブネットを照合してください。リンク先の検証では、ホスト側でタグを付ける VLAN に対し、ゲスト側は通常タグなしのインターフェースを使います。

ゲスト・ネットワーク管理者が、そのゲストから指定した相手とアプリケーションサービスをテストします。名前解決の応答、選択されたアドレスファミリー、宛先、プロトコル・ポート、結果を別々に記録してください。名前とアドレスで結果が違う場合は、DNS とアプリケーション・TLS の識別情報を調べてから判断します。HTTPS に IP だけでアクセスすると、証明書や仮想ホストの動作が変わる場合があります。成功と見なすために証明書検証を回避しないでください。ping の成功だけではサービスの動作を証明できず、失敗だけでは隔離を証明できません。承認された宛先だけをテストし、隔離が必要な場合は管理者が指定した接続禁止先も確認します。

同じホスト上の相手への成功では物理接続をテストできません。ホスト間・ホスト外のテストには、特定された相手と承認済みのスイッチ経路が必要です。診断の思いつきでワークロードを移行しないでください。予期しない本番環境へのアクセスがあれば証拠を保全し、使い捨ての検証ゲストを通常停止します。管理・ストレージに影響がある場合は、追加変更の前に独立したコンソールと管理者の復旧計画を使ってください。

### 4. 管理者が選んだ修正を確認する

正確な対応関係、時刻、エラー、比較結果を担当管理者へ渡します。合意した修正を、ゲスト・ストレージ・ホスト・ネットワークの該当手順で適用してください。この調査は汎用的なリセットを指示するものではありません。その後、一覧を更新し、**同じ送信元から同じ宛先へのサービスのテスト**、必要な隔離確認、管理・ストレージへのアクセス確認を繰り返します。変更内容と観測結果を記録してください。緑色の表示だけでは解決とは言えません。経路が不明なままならインシデントを継続し、機密情報を除いた報告を共有します。実機での障害・復旧の受け入れ検証は未完了です。

## NFS フルバックアップの失敗を調べる {#backup-failures}

XOA-HL 管理者アカウントで、[NFS フルバックアップのラボジョブ](/docs/xoa-hl/backup-restore/)だけを対象にします。ジョブとスケジュールの ID、元 VM の UUID、リモート ID、タイムゾーン付きの予定時刻、最後の隔離復元の結果を用意してください。調査は**ブラウザー**で行い、ストレージの確認は対象システムの管理者に依頼します。障害を意図的に起こす必要はありません。差分チェーン、レプリケーション、本番環境の復旧には別の手順が必要です。


[増分バックアップとチェーンの復旧を検証する](/docs/xoa-hl/backup-restore/#delta-backups)。

### 1. 実行を特定して詳細を保存する

1. **バックアップ → オーバービュー** (`/#/backup/overview`) でジョブを探し、その下の **Logs** 表を確認します。必要に応じてログの検索・状態フィルターを消し、ジョブと開始時刻を照合します。表のジョブ ID は短縮表示なので、名前だけでなく詳細の完全な ID を使います。
2. 実行の状態ボタンを選んで詳細を開きます。`id`、`jobId`、`scheduleId`、開始・終了時刻、状態を記録します。変更前にクリップボードか **Download log** で JSON を非公開で保存してください。報告用には機密情報を除いた抜粋を作ります。ダウンロード時に機密情報が自動で削除されるわけではありません。
3. 詳細の検索を消し、すべてのタスク状態を選択します。VM タスクの全ページを確認してください。最初は実行中・失敗・中断したタスクだけが表示される場合があり、1 ページは 5 件です。VM の UUID を照合し、スナップショット、リモート先・エクスポート、転送のタスクを確認します。関係する階層のエラー、スキップ理由、警告を保存します。生のタスクすべてが画面に表示されるとは限らないため、ツリーが不完全なら保存した JSON も確認してください。

**確認：** 記録から特定の実行と対象 VM・リモート先を識別できます。ログやタスクがないことは、処理が行われなかった証拠にはなりません。

### 2. 再試行前に状態の意味を確認する

以下は ce38 のカタログに基づく実際のラベルです。**Started** はフランス語では **Démarré**、日本語では **スタートしました** です。以下のほかのジョブ状態、**Logs**、**Download log** は、この版では英語にフォールバックします。

| 状態ラベル / JSON の値 | 意味と次の確認 |
| --- | --- |
| スタートしました / `pending` | 実行中として記録されています。更新して進捗を確認します。終了時刻がないことは成功を意味しません。別の実行を開始しないでください。 |
| Successful / `success` | 記録された実行とタスクが正常終了しています。警告と新しい復元ポイントを確認し、ゲスト・データの復旧は別途検証します。 |
| Skipped / `skipped` | 処理が省略されています。理由を確認してください。このソースは `no disks found`、`no VMs match this pattern`、`unhealthy VDI chain` などをスキップとして扱います。新しい検証済みバックアップには数えません。 |
| Failed / `failure` | 実行または子タスクが失敗しました。ほかの処理が成功している場合もあるため、対象の段階と実際のバックアップ一覧を調べます。 |
| Interrupted / `interrupted` | 開始に対応する完了記録がなく、サーバーもその実行を実行中と認識していません。サーバーの時系列と部分的なオブジェクト一覧を保存します。この状態はロールバックや安全な再試行の証明にはなりません。 |
{.xoa-backup-diagnosis}

### 3. 失敗した段階と残ったデータを分けて確認する

復元ポイント一覧と復元ログは **バックアップ → 復元** (`/#/backup/restore`) で確認します。

| 観察した状況 | 対処を選ぶ前の確認 |
| --- | --- |
| 対応する実行がない | ログフィルター、ジョブ・スケジュール ID、有効状態、タイムゾーン、サーバーの稼働、[保存したスケジュール](/docs/xoa-hl/backup-restore/#backup-schedules)を再確認します。自動的な追いつき実行やメール通知を前提にしません。 |
| VM・スナップショットのエラー、VM のスキップ | 選択した VM の UUID、ディスク、ホスト接続、元 SR の容量を確認し、正確な理由を保存します。一般的な対処としてスナップショットを削除したり VDI チェーンを操作したりしないでください。 |
| リモート先・エクスポート・転送のエラー | ストレージ管理者と、アプライアンスから NFS への接続、エクスポートの権限・オプション、リモート先の容量を確認します。リモートテストの成功は、エクスポート全体や復元の成功を証明しません。 |
| 転送が成功した後に実行が失敗 | **Delete first** がオフの場合、このフルバックアップ処理はエクスポートとメタデータを書いた後で古いポイントを削除します。後の削除が失敗しても新しいポイントが残る場合があります。再実行やファイル削除の前に時刻と残存ポイントを確認します。 |
| Restore にポイントがない | **バックアップ → 復元** を開いて更新します。対象リモートが有効か、読み込みエラーがないか確認します。読み取れないリモートは一覧に出ない場合があります。空の一覧はバックアップが削除された証拠ではありません。 |
| 復元が失敗 | 同じページの復元ログ、リモートの読み取り、復元先 SR・ホストへのアクセスを確認し、部分的な VM・ディスクを UUID で記録します。元 VM とバックアップを保全し、名前だけで削除しないでください。 |
{.xoa-backup-diagnosis}

**確認：** 失敗した段階、残った復旧ポイント、状態不明のオブジェクトを区別できます。ファイルや一覧のポイントだけではデータが復旧可能と証明できません。

### 4. ラボで対処して結果を検証する

1. 今後の起動を一時停止する場合は、オーバービューで対象ラボスケジュールを無効にし、更新して状態を確認します。無効化は実行中の処理をキャンセルしません。この版ではオーバービューのキャンセル操作が無効です。`xo-server` の再起動はバックアップのキャンセルや後片付けの手順ではありません。
2. 特定した接続・容量・選択の問題を担当者と解決し、ジョブ、スケジュール、VM、リモート先を再確認します。**Delete first** はオフのままにし、必要な復旧コピーをジョブの保持設定の対象外に保全してください。処理の実行状態や部分的なオブジェクトの所有関係が不明なら、記録を保存して支援を求めてから再試行します。
3. 実行中の処理がなく状態を把握できたら、チュートリアルの通常の手動実行を使い、1 VM のラボジョブを実行します。詳細画面の restart・force 操作は**バックアップを実行する操作**で、ゲストの再起動ボタンでも読み取り専用診断でもありません。この手順では force を使いません。再試行で保持対象が変わらないとも保証しません。
4. 新しい実行とポイント一覧を調べ、[停止したコピーを復元して全 NIC を削除し、確認用データを照合](/docs/xoa-hl/backup-restore/)します。ラボスケジュールは無効のままにしてください。予定実行の再開を検討する前に、元のエラー、対処、新しい実行・ポイント ID、隔離復元の結果を記録します。

**確認：** 対処後の実行、残存ポイント一覧、隔離したゲスト・データの復元がすべて成功します。成功しなければ障害を未解決のままにし、[機密情報を除いた記録を報告](#問題を報告する)してください。このプレビューのアプライアンスでの障害・復旧検証と人による言語レビューは未完了です。

## アプライアンスの読み取り専用診断

許可されたコンソールまたは SSH セッションを使い、必要に応じて root 権限を使います。最初の確認前や再起動後に実行時の状態ファイルがなくても、それ自体は障害の証拠ではありません。`systemctl status` が非ゼロを返した場合は、停止中や失敗状態の場合があります。表示された状態を読んでください。

```bash
rpm -q xoa-hl nodejs
timedatectl
df -h
systemctl status xo-server redis xoa-hl-update.service --no-pager
systemctl list-timers 'xoa-hl-*'
journalctl -u xo-server -u xoa-hl-check-update.service -u xoa-hl-update.service -u xoa-hl-auto-update.service --since '1 hour ago' --no-pager
tail -n 100 /var/log/xoa-first-boot.log
tail -n 100 /var/lib/xoa-hl/update.log
cat /run/xoa-hl/status
cat /var/lib/xoa-hl/auto-update.status
```

エラーを消す目的でデータベース、ログ、ロックを削除しないでください。ディスクが満杯の場合は、増加しているファイルを特定し、記録を保存してから削除対象を判断します。状態の意味と更新・再起動の判断は[保守](/docs/xoa-hl/maintenance/)を参照してください。自動実行の状態は過去の記録の場合があるため、UTC の時刻を照合します。

## よくある質問

**更新が表示されているのに確認コマンドが 100 を返すのはなぜですか？** パッケージの確認処理は `dnf check-update` の終了コード 100 を `AVAILABLE`、0 を `UP_TO_DATE`、その他を `ERROR` に変換します。更新があることはインストールの失敗ではありません。

**Stable に戻すと testing の更新が取り消されますか？** いいえ。チャネルは次回以降の確認・インストールで使うリポジトリを選びます。stable への変更はインストール済み候補版をダウングレードしません。

**設定エクスポートは VM バックアップやアプライアンスのロールバックに使えますか？** 代わりにはなりません。[設定の対象範囲と復旧の制約](/docs/xoa-hl/configuration-backup/)を確認し、ゲストのバックアップは別途保存します。

## 問題を報告する

[XCP-HL の Issue を作成](https://github.com/Vagrantin/xcp-hl/issues/new)し、次の情報をテキストで記載します。

- ページの URL と表示言語、または問題が起きたアプライアンス画面のパス。
- イメージタグ、About のバージョン、インストール済み RPM・Node のバージョン、stable/testing チャネル。
- 操作、正確な手順、期待した結果、実際のエラー。
- タイムゾーン付きの時刻、手動・自動モード、関連サービスの状態、機密情報を除いたログの抜粋。
- 使い捨て環境で再現するかどうかと、最後に正常動作したバージョン。

ログやスクリーンショットからパスワード、トークン、Cookie、非公開のホスト名・アドレス、ユーザー・ゲストのデータを除いてください。`xo-server` と初回起動のログは認証情報を含む可能性があります。設定エクスポート、TLS 秘密鍵、設定ファイル全体は添付しないでください。元の記録は非公開で保管します。
