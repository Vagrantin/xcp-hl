テスト VM を別のストレージへ完全バックアップし、コピーを復元してデータが利用できることを確認します。バックアップジョブの成功は確認の始まりです。復元によって確認を完了します。

{{< callout type="info" >}}
プレビュー手順：XO 5.113.2（`e281c536`）、XOA-HL パッケージ `v5.113.2_e281c536-ce38`、イメージ `xoa-image-20261009-5f33c81` のソースを確認しています。使い捨ての検証環境での実行は未完了です。セクション 1–6 は NFS への VM 完全バックアップ、セクション 7 は別の増分バックアップ検証、セクション 8 はその差分バックアップからの 1 ファイルのダウンロード、セクション 9 は SR への完全レプリカの検証です。他の保存先やモードには個別の検証が必要です。
{{< /callout >}}

## 始める前に

- [テスト VM を作成して OS をインストールします](/docs/xoa-hl/create-vm/)。XOA-HL の管理者アカウントを使用します。このバージョンのバックアップ画面には管理者権限が必要です。
- 元の VM とアプライアンスを保持するストレージとは別のバックアップシステムで、NFS エクスポートを用意します。アプライアンスから接続でき、バックアップファイルの作成、読み取り、削除ができる必要があります。サーバー、エクスポートパス、必要なマウントオプションをストレージ管理者に確認してください。
- 保存先、作業用スナップショットを置く元の SR、復元ディスクを受け入れる書き込み可能な SR の空き容量を確認します。保持数と次のバックアップ実行分の容量を確保してください。圧縮後のサイズは保証されません。
- ゲスト内に機密情報を含まない小さなファイルを作成し、内容またはチェックサムを記録して、バックアップ前に書き込みを完了します。初回テストではゲストを正常にシャットダウンし、VM が停止していることを確認します。稼働中のバックアップがアプリケーション整合性を持つと仮定しないためです。
- 2 台目の VM のリソースを確保します。復元したコピーは、**すべての仮想 NIC を削除するまで停止状態**にします。このコンソールのみのテストにはゲストネットワークは不要です。

管理操作は **ブラウザー** で行います。サンプルファイルの作成と確認は **ゲスト VM** 内で行います。ホストやアプライアンスでのシェルコマンドは不要です。

## 1. バックアップ保存先を追加する

1. **設定 → リモート**（`/#/settings/remotes`）を開きます。確認済みの適切な保存先があれば再利用し、なければ `lab-backup-nfs` という名前で作成します。
2. **NFS** を選択し、管理者から指定されたサーバーとエクスポートパス、必要なマウントオプションを入力します。ストレージ構成で必要な場合を除き、詳細項目は既定値のままにします。このテストではアプライアンス内のローカルディレクトリを選ばないでください。
3. 保存し、必要なら有効化して、**リモートのテストをすると良いでしょう**を実行します。接続やテストにエラーがあれば、続行する前に確認します。

**確認：** 保存先が有効で、テストが成功し、接続エラーが表示されません。これはアクセスの確認であり、VM バックアップを復元できることの証明ではありません。

この ce38 の固定ソースでは、フランス語のリモートテスト成功・失敗の見出しが継承カタログで逆になっています（[修正の追跡](https://github.com/Vagrantin/xoa-hl/issues/38)）。見出しだけで判断せず、成功・エラーのアイコンとエラー・処理段階の詳細を確認します。実際のバックアップと隔離した復元も必要です。ここでは実機での修正適用を確認したとは主張しません。

## 2. 完全バックアップジョブを 1 つ作成する

1. **バックアップ → バックアップの作成 → VMs**（`/#/backup/new/vms`）を開き、ジョブ名を `lab-first-vm-full` にします。
2. テスト VM だけを明示的に選択します。別の VM を含めないよう、スマート選択は無効にします。
3. モードで **バックアップ**を選択します。**Rolling snapshot**、**Delta backup**、**Disaster recovery**、**Continuous replication** は無効のままにします。この画面では **バックアップ** が完全エクスポートのモードです。
4. **Target remotes (for export)**（エクスポート保存先）で `lab-backup-nfs` を選択します。**古いバックアップを最初に削除する** は無効にします。有効にすると、新しいエクスポートが成功する前に以前のコピーが削除される可能性があります。
5. スケジュールを明示的に追加します。この小規模な検証例では **Backup retention**（バックアップ保持数）を `2` にし、`Asia/Tokyo` などのタイムゾーンを選択して、次回実行のプレビューを確認します。保持数はそのスケジュールで保持するバックアップの個数であり、日数ではありません。
6. ジョブを保存する前に、スケジュール一覧でそのスケジュールを無効にします。最初のバックアップ・復元確認は手動で行います。セクション 6 の監視付きの練習までは、スケジュールを無効のままにしてください。
7. 保存後、概要で対象 VM が 1 台、保存先が正しく、スケジュールが無効であることを確認します。初回テストでは詳細設定を変更しません。

{{< callout type="warning" >}}
保持数の設定によって、次の実行で古いバックアップが削除される場合があります。検証専用の保存先を使用し、この例のために本番ジョブの保持数を減らさないでください。元の SR にあるスナップショットは独立したバックアップではありません。
{{< /callout >}}

## 3. バックアップを実行して確認する

1. **バックアップ → オーバービュー**（`/#/backup/overview`）で、無効にしたスケジュールの実行操作を選択します。確認画面が対象ジョブと VM 1 台を示すことを確認して実行します。
2. 完了まで待ちます。ログを開き、開始したという表示だけでなく、VM とエクスポートの結果を確認します。警告、失敗、スキップされたデータを調べます。
3. **バックアップ → 復元**（`/#/backup/restore`）を開きます。テスト VM を見つけ、期待した時刻と保存先で新しい完全バックアップが表示されることを確認します。必要に応じて一覧を更新します。

**確認：** 実行が成功し、新しい復元ポイントが表示されます。ジョブ、スケジュール、保存先、バックアップ時刻、インストール済みバージョンを記録します。元のゲストは正常に起動して構いません。復元テスト中はスケジュールを無効のままにします。

## 4. 停止したコピーを復元する

1. **バックアップ → 復元** でテスト VM の復元操作を選び、作成したばかりの完全バックアップを正確に選択します。
2. 十分な空き容量がある書き込み可能な SR を選びます。これは VM ディスク用のストレージであり、NFS バックアップ保存先や ISO SR ではありません。
3. **Start VM after restore**（復元後に VM を起動）は **無効** にします。**Generate new MAC addresses** を有効にして、コピーに別の MAC アドレスを割り当てます。MAC アドレスを変えても、ゲストの固定 IP、ホスト名、アプリケーションの識別情報は変わりません。
4. 復元を確定し、完了まで待ちます。復元ログにエラーがないか確認します。新しい VM は UUID と復元ディスクで識別し、名前だけで判断しないでください。
5. 復元 VM が停止していることを確認します。コピーの名前を `lab-first-vm-restore-test` に変更し、元の VM とは異なる UUID を両方記録します。

**確認：** 期待したディスクを持つ、別の停止した VM が存在します。まだ起動しないでください。予期せず稼働している場合はコピーを停止し、続行前にネットワークへの接続状況を調査します。

## 5. コピーを隔離して起動し、確認する

1. **復元したコピーのネットワーク** タブ（`/#/vms/<restored-uuid>/network`）を開きます。停止中に仮想 NIC を **すべて** 削除し、一覧が空であることを確認します。実行時の「未接続」状態だけでは、次回起動後の隔離を保証できません。
2. 復元 UUID と空の NIC 一覧を再確認し、コピーを起動して **コンソール** を開きます。元の VM のネットワークは変更しません。
3. ゲストの起動、コンソールログイン、サンプルファイルの内容またはチェックサムを確認します。復旧目標に必要な他のデータも確認してください。起動できるだけでは、アプリケーション全体の復旧確認は完了しません。
4. 復元ゲストを正常にシャットダウンします。結果、バックアップ時刻、復元所要時間、バージョンを記録します。終了後、UUID を確認してテスト用コピーとその復元ディスクだけを削除します。元の VM とバックアップは残します。

**確認：** 復元データが記録したサンプルと一致し、テスト VM は NIC がない状態で起動しました。失敗した場合はバックアップを保持し、コピーを停止してログを確認してから再試行します。

## 6. バックアップのスケジュールと保持数を確認する {#backup-schedules}

自動実行を有効にする前に、上記の手動バックアップと隔離した復元を完了します。その NFS 完全バックアップ用の検証ジョブ、明示的に選択した使い捨て VM 1 台と、無効なスケジュール 1 件だけを使います。この練習のすべての実行では元のゲストを正常に停止したままにし、稼働中・アプリケーションの整合性は個別に確認します。空き容量と保存先へのアクセスを再確認し、必要な復旧用コピーは**このジョブの保持ポリシーの対象外**に保管します。

1. **バックアップ → オーバービュー** でジョブ ID を記録し、クリップボードのボタンで正確なスケジュール ID をコピーします。ジョブの編集を開き、**Schedules** で既存の無効な行を編集します。削除して作り直さないでください。明確な検証名を付け、**Backup retention** を `2` に保ち、**古いバックアップを最初に削除する**、長期保持と自動復元ヘルスチェックはオフにします。完全 **バックアップ** モード、対象 VM と `lab-backup-nfs` だけが選ばれていることを確認します。
2. 時刻の選択画面で検証用のルールを作り、**Timezone** を `Asia/Tokyo` など明示的に選択します。実測した手動バックアップ時間より長い間隔を取り、失敗の調査時間も確保します。監視する検証時間内の次の実行を少なくとも 3 回分確認し、生成された **Cron pattern** を記録します。ここでは本番向けの共通間隔を定めません。この版では **Schedules**、**Backup retention**、**Timezone**、**Cron pattern**、**Enabled**・**Disabled** は英語表示のままです。
3. ブラウザーのタイムゾーンも記録します。ルールは指定したタイムゾーンを使いますが、プレビューは得られた日時をブラウザーの表示タイムゾーンで示します。時計の表示が違っても、実行する瞬間が異なるとは限りません。有効にする前に予定の実行時点とアプライアンスの時計を照合してください。プレビューは日時の予測であり、実際のバックアップ実行を証明しません。
4. 編集画面では行を **Disabled** に保ち、ジョブの **バックアップジョブの保存** を選びます。再度開いてスケジュール ID、ルール、タイムゾーン、保持数、VM と保存先を読み返します。スケジュールとジョブは別のリクエストで保存されるため、エラーでは一部だけ変更される場合があります。値が一致するまで有効にしません。
5. **オーバービュー** に戻り、そのスケジュールだけを状態ボタンで有効にします。このボタンはすぐに変更を送信し、別の保存操作はありません。更新して記録した行の **Enabled** を確認します。手動実行ボタンを押さず、次の定期実行を観察してください。該当スケジュールの実行詳細を開き、ジョブ・スケジュール ID、実際の開始・終了時刻、対象 VM とエクスポート結果を確認します。正しい保存先の **復元** に新しいポイントがあることも確認します。
6. 同じスケジュールで少なくとも 3 回の実行が成功するまで観察し、毎回、復元ポイントの時刻を比較します。保持数 `2`、長期保持なしで削除処理も成功した場合、期待される結果はこの保存先の VM・スケジュールに該当する最新の完全バックアップ 2 個です。ファイル数を固定値と仮定したり、失敗・スキップを確認済みの復旧ポイントとして扱ったりせず、結果を検証します。**古いバックアップを最初に削除する** がオフの場合、確認したソースは新しいエクスポートとメタデータを書いてから選択した古いコピーを削除します。削除も失敗し得るため、ログと一覧を別途確認します。
7. 次の予定時刻より前に、**オーバービュー** で正確なスケジュールを無効にし、更新して **Disabled** を確認します。無効化は将来の実行を止めますが、実行中のジョブをキャンセルしません。この版のオーバービューのキャンセル操作は無効です。実行中の検証ジョブは完了を待って結果を調べ、その次の予定時刻で新しい実行がないことを確認します。終了時はルールを無効のままにします。
8. 定期実行による保持済みポイントを選び、セクション 4–5 を繰り返します。停止状態で復元し、初回起動前に継承した NIC をすべて削除し、サンプルのチェックサムを比較してコピーをシャットダウンします。特定済みのコピーの片付けには[使い捨て VM の削除手順](/docs/xoa-hl/vm-operations/)を使用します。最後のスケジュール状態、残ったポイントと復元結果を記録します。

後続の削除が失敗して実行全体がエラーになっても、新しいエクスポートが残る場合があります。再試行前に実際のポイント・ファイル一覧を確認し、使用可能と数える前に隔離した復元で証明します。

保持数の対象は VM、完全バックアップのモードと**保存先ごとのスケジュール ID**であり、表示名や全体の日数・ファイル数ではありません。別のスケジュールが別のポイントを保持する場合があります。同名のルールでも削除・再作成すると ID が変わるため、片付けの近道にしたり、旧バックアップが新しいポリシーに入ると仮定したりしません。この練習は長期保持の期間別枠やデルタチェーンを検証しません。

予定した実行がない場合、保存・状態変更や実行が失敗した場合は、ジョブ・スケジュール・保存先 ID、予定・実際の時刻、エラーと一覧を保存します。状態が確定するまでは自動実行される可能性があると扱います。再試行前にサーバーの稼働・時計、有効状態、VM 選択、保存先アクセスと容量を確認してください。すでに実行中のジョブへのトリガーは拒否されることがあり、重複の待ち行列、再試行やアプライアンス停止中の未実行分の自動再実行を仮定しません。無効化、ルール変更やジョブ削除は実行中のキャンセル手順ではありません。原因を解決したら、実行中のジョブがない状態で一度だけ手動実行し、ポイントと隔離した復元を確認してから合意したスケジュールを再開します。メール・通知、夏時間の切り替え、停止後の回復と本番の保持ポリシーには個別の受け入れ確認が必要です。

## 7. 増分バックアップとチェーンの復旧を検証する {#delta-backups}

上記の完全バックアップと隔離した復元が成功してから、別の **NFS delta バックアップ検証**を行います。独立した完全バックアップは現在の保存先に残してください。完全モードの XVA エクスポートは、新しい delta ジョブの最初の親にはなりません。delta の復元ポイントにはメタデータと必要な VHD 親チェーンが必要です。VHD を一つコピーしただけでは VM 全体のバックアップになりません。

通常の仮想ディスクを持つ使い捨て VM を使い、共有・パススルーディスクやメモリ・チェックポイントのバックアップは対象外とします。VM・VDI UUID、サイズ、ゲストのサンプルファイルのパスとチェックサムを記録し、検証中はディスク構成を変えないでください。ストレージ管理者が承認した空の専用 NFS エクスポートと、`lab-delta-nfs` などの新しい保存先を用意します。ソースのスナップショット領域、保存先の完全エクスポートと後続の書き込み・マージ領域、隔離した復元用 SR の容量を確保します。本番用の保持ポリシーではありません。

管理操作は管理者アカウントで **XOA-HL のブラウザー**から行い、サンプルの変更とチェックサム確認は**ゲストコンソール**で行います。実際のリリース・UI と利用可能な機能を記録してください。**Delta Backup** や設定項目が利用できなければ停止し、実際のビルド・プラン状態を報告します。ライセンスを変更したり XO 6 の手順に置き換えたりしないでください。ソースに存在しても、実機でのサポート確認にはなりません。

### 別のジョブを作成し、スケジュールを無効にする

1. セクション 1 と同様に専用の保存先を追加してテストします。**バックアップ → バックアップの作成 → VMs** (`/#/backup/new/vms`) を開き、`lab-delta-chain` という名前で検証用 VM 一台だけを明示的に選びます。スマート選択は無効のままにします。
2. **Delta Backup** だけを選びます。**バックアップ**、**Rolling Snapshot**、**Disaster Recovery**、**Continuous Replication** は無効にします。保存先は `lab-delta-nfs` のみとし、**古いバックアップを最初に削除する** は無効のままにします。以前の完全バックアップのジョブを変更・変換しないでください。
3. **詳細設定** で **Full backup interval** を `2` にします。この検証では **Use NBD to transfer disk if available** と **Purge snapshot data when using CBT.** を無効にし、**Merge backups synchronously** を有効にします。オフライン・メモリバックアップ、自動ヘルスチェック、その他の詳細設定は使いません。このジョブが保持するスナップショットを手動削除しないでください。
4. **Backup retention** を `2` にしたスケジュールを一つ追加し、タイムゾーンと次回実行の予測を確認します。**Force full backup** は無効にします。これを有効にすると、スケジュール側の設定が間隔を上書きし、毎回完全バックアップになります。長期保持は無効にします。保存前にスケジュールを無効化し、保存後に編集画面を開き直して VM、保存先、間隔、各設定、無効状態を確認します。ジョブ・スケジュール・保存先 ID を記録し、この手動検証中はスケジュールを無効のままにします。

このバージョンの FR/JA カタログでは、間隔、NBD、CBT データの削除、同期マージ、Force、差分復元の設定名は英語にフォールバックします。間隔はチェーンの長さに関する設定で、日数や保持する復元ポイント数ではありません。新しいジョブで同じディスク構成を使う今回の検証では、間隔 `2` により完全なキーエクスポート、増分エクスポート、次の完全なキーエクスポートの順になる想定です。ベースの欠落、ディスクの変更、エラーで結果が変わる場合があるため、ログで確認してください。

### 区別できる三つのポイントを作る

毎回、無害なサンプルを書き終えてから元のゲストを通常停止します。先行するバックアップやマージが動いていないことを確認し、通常の手動実行を使います。この検証ではジョブのオフラインバックアップモードを有効にせず、ゲストの強制停止も行いません。実行 ID、時刻、VM・スケジュール・保存先、エクスポートの **Type**、警告、作成されたポイントの識別情報を記録します。タスクの全状態・全ページを確認し、必要なら生の JSON を保存してください。delta ジョブのポイントは、実際のエクスポートが完全でも復元選択欄に **incremental** と表示される場合があります。そのモード表示やファイルサイズだけでエクスポート種別を判断しないでください。

| 実行 | 通常停止前のゲストのサンプル | 期待する観測 |
| --- | --- | --- |
| 1 | バージョン A とチェックサム A | 新しいジョブの完全なキーエクスポート、ポイント A が一覧にある |
| 2 | 元の VM を起動し、B を書き、チェックサム B を記録して停止 | 利用可能なベースを使う増分エクスポート、ポイント B が一覧にある。実行 3 の前に下記の隔離した復元を行う |
| 3 | 元の VM を起動し、C を書き、チェックサム C を記録して停止 | 間隔 `2` による完全なキーエクスポート。クリーンアップ・マージ結果と保持された B/C を調べ、下記の復元を繰り返す |

実行 2 が full と表示されたり、完全エクスポートへのフォールバック警告が出たりした場合は記録を保存し、ベースのスナップショット・保存先の親、ディスク構成、保存された間隔・Force 設定を確認します。その実行を増分転送の実証とは数えないでください。テストのためにベースを削除してはいけません。

保持処理は、その保存先にある VM・スケジュールの対象 delta ポイントを選びます。マージ数の制限やクリーンアップの失敗により、余分なポイントが残る場合があります。**古いバックアップを最初に削除する** が無効なら古いポイントの削除は転送・チェーン接続の後ですが、実行前のクリーンアップでもデータのマージ・削除やメタデータ修正が起こり得ます。同期マージでも処理全体の原子性や復旧成功は保証されません。個別のバックアップ JSON・VHD の削除、改名、移動、編集や、チェーン整理のためのスナップショット削除を行わないでください。

### 保持処理の前後で増分ポイントを復元する

1. **バックアップ → 復元** (`/#/backup/restore`) で `lab-delta-nfs` の正確なポイント B を選び、十分な容量がある書き込み可能な SR を指定します。**必要な全ディスク**を含めてください。delta の画面ではディスクを除外できるため、各ディスクの保存先を確認し、欠落を許可しないでください。
2. **Start VM after restore** と **Use differential restore** は無効にし、**Generate new MAC addresses** を有効にします。差分復元はソース側のスナップショットを再利用する場合があり、別の検証です。保存先のバックアップチェーンから復元するための必須条件ではありません。
3. セクション 4–5 の隔離確認を行います。新しい VM・ディスク UUID を記録し、コピーが停止していることを確認します。起動前に継承された NIC を**すべて**削除し、コンソールからサンプルをチェックサム B と比較します。コピーを通常停止し、元の VM とバックアップを維持します。各コピーを個別に識別し、承認済みの片付けには [VM 削除の手順](/docs/xoa-hl/vm-operations/) を使ってください。
4. 実行 3 とクリーンアップ・マージの完了確認後、保持された B を新しい停止済み・隔離済みのコピーに再度復元し、チェックサム B を確認します。C も別に復元してチェックサム C を確認します。残るポイントと結果を記録してください。これにより最新のキーエクスポートだけでなく、保持処理後の古い増分ポイントを確認します。スケジュールは無効のままにします。

親の欠落、転送・マージエラー、復元失敗があれば、実行 JSON、ポイントの識別情報、途中で作成された VM・ディスクの一覧を保存します。再実行で保持状態やチェーンが変わる可能性があるため、それ以上の手動実行を止めてください。バックアップ管理者とアクセス・容量・所有関係を解決してから、不明なチェーンファイルを変更せずに検証を繰り返します。汎用的な対処としてサービス再起動や強制・修復操作を行わないでください。復旧を確認できなければ独立した完全バックアップを残し、インシデントを継続します。実機の障害・復旧、稼働中ゲストの整合性、NBD/CBT、暗号化・他の保存先、差分復元は別途検証が必要です。

## 8. 差分バックアップから 1 ファイルをダウンロードする {#file-restore}

ソース確認済みの**ファイル単位の復元検証**です。セクション 7 のチェーンと隔離した VM 復元を確認した後、保持されているポイント B を使用します。**ファイル単位の復元**画面には delta モードのバックアップだけが表示され、セクション 1–6 の完全バックアップの XVA は表示されません。ブラウザーの作業端末へアーカイブをダウンロードする操作であり、元の VM 内へファイルを戻す操作ではありません。ポイントが表示されてもディスクの読み取り成功は証明されません。インストール済み環境の機能、権限、ファイルシステムやツールの対応は、使い捨て環境で確認が必要です。

単一ディスクで読み取り可能な通常のパーティションを持つ Linux テスト VM の小さな通常ファイルを使います。B のバックアップ前に、バージョン B のゲスト内パス、内容、SHA-256 を記録します。例は `/home/lab/recovery-b.txt` です。ポイント B と保存先のチェーンを保持し、端末にアーカイブ用の空き容量を用意します。XOA-HL 管理者アカウントで、実際のビルドに**ファイル単位の復元**があることを確認します。初回検証には本番 VM、機密ファイル、暗号化/RAID ボリューム、シンボリックリンク、ディレクトリを使いません。すべてのファイルシステム、LVM 構成、保存先の対応をこの手順から推定しないでください。

1. **バックアップ → ファイル単位の復元** (`/#/backup/file-restore`) を開きます。使い捨て VM のファイル復元操作を開き、隣の削除操作には触れません。VM またはポイントがない場合は、有効な `lab-delta-nfs` の更新・確認と、セクション 7 のジョブ/ポイント一覧を確認します。前の完全バックアップは選びません。
2. 時刻とジョブから**正確なポイント B**を選び、想定するディスクを選びます。パーティションの検出を待ち、表示された場合は確認用ファイルがあるパーティションを選びます。パーティション表のないディスクでは、生のファイルシステムを直接参照できる場合があります。検出や一覧のエラーが出たら停止し、バックアップファイルを手動でマウント・編集しません。
3. `/` からフォルダーをたどり、B の確認用ファイル**だけ**を選びます。フォルダー全体や全ファイルの選択は使いません。パスとアーカイブ形式の **tgz** (既定値) を確認します。**zip** も選べますが遅くなる場合があります。復元/ダウンロードを開始し、ブラウザーで完了を待ちます。ポップアップやダウンロードがブロックされた場合、または転送が途中で終わった場合は成功ではありません。
4. 作業端末でアーカイブのファイル名、サイズ、SHA-256 を記録します。中のエントリを調べ、新しい使い捨てディレクトリへ想定したファイルだけを取り出し、バックアップ前に記録した B の内容と SHA-256 に照合します。アーカイブ内のパスは信頼せず、稼働中のデータへ展開しません。ファイル名だけの一致やバージョン C の内容では合格しません。元の VM、ポイント B、スケジュールは変更しません。

**合格条件:** 保持された正確な B、ディスク、パーティションを記録し、ダウンロードしたアーカイブが開けて想定したファイルだけを含み、内容が B の SHA-256 と一致します。インストール済みバージョン、VM/ジョブ/保存先/ポイントの ID と時刻、ディスク/パーティション、選択パス、画面エラー、アーカイブのハッシュ、抽出ファイルの照合結果を残します。選択、パーティション検出、保存先/チェーンの読み取り、転送、照合が失敗したら証拠を保存し、管理者の調査まで追加のバックアップ/保持処理を止めます。ポイントを表示させるためにチェーンの JSON/VHD、元のスナップショット、途中のファイルを削除しません。回収したファイルをゲストへコピーするのは、担当者の承認を要する別の復旧作業です。

## 9. 別のプールで DR の完全レプリカを検証する {#dr-replica}

この**ソース確認済みのプレビュー**は **Disaster Recovery** (DR) によるターゲット SR への完全モードのコピーを扱います。NFS バックアップとも、差分転送と別のチェーン規則を使う **Continuous Replication** (CR) とも異なります。レプリカは停止中の VM で、バックアップ処理によって起動操作がブロックされています。**保持中のレプリカのブロックを解除したり、直接起動したりしないでください**。ソースコードでは、利用する際はクローンを作るよう指示しています。このラボで確認するのは隔離したターゲットでのクローンであり、自動フェイルオーバー、サービス継続、元プール喪失時の復旧、フェイルバックではありません。

プール A の使い捨て VM と、同じ XOA-HL アプライアンスに接続した別の使い捨てプール B を使います。ターゲット管理者に、B の書き込み可能な VM ディスク用専用 SR `lab-dr-sr` を承認してもらい、完全コピー 2 個と検証用クローンの容量を確保します。A とは別のストレージ障害領域に置き、ISO ライブラリや元の SR は使いません。両プール/SR の UUID、容量、ターゲットホストからの接続を記録します。セクション 1–5 の独立した NFS 完全バックアップも保持します。管理者アカウント、共有/パススルーディスクのない通常の単一ディスク VM を使い、無害な A/B/C の確認用データと SHA-256 を各回の正常シャットダウン前に記録します。コンソールと**本番ネットワークのない**ターゲットを用意し、起動前に停止したクローンから継承した NIC をすべて削除します。インストール済みビルドで DR と両プールが実際に利用できることを確認し、操作項目や SR がなければ停止します。

1. **バックアップ → バックアップの作成 → VMs** (`/#/backup/new/vms`) で新規ジョブ `lab-dr-full` を作り、VM を明示的に 1 台だけ選び、スマート選択は無効にします。**Disaster Recovery** だけを有効にし、**バックアップ**、**Delta Backup**、**Continuous Replication**、**Rolling Snapshot** は無効にします。**Target SRs (for replication)** で `lab-dr-sr` だけを選びます。転送前に旧レプリカを意図的に削除しないよう、**古いバックアップを最初に削除する**は無効のままにします。NFS/差分ジョブは編集しません。
2. **Replication retention** を `2` とし、タイムゾーンと次回実行のプレビューを確認したスケジュールを 1 つ追加します。スナップショット保持とヘルスチェックは使いません。保存前にスケジュールを無効にし、保存後に再度開いて VM、SR、モード、保持数、無効状態、ジョブ/スケジュール ID を確認します。ターゲット SR と保持数の UI ラベルは FR/JA でも英語のままになる場合があります。手動検証中は無効を維持します。
3. 元のゲストに A を書き込んで正常停止した後、**バックアップ → オーバービュー**からジョブを 1 回実行します。VM/エクスポートの各タスクと警告を調べ、B プールで VM UUID、ジョブ名/時刻を含む名前、**Disaster Recovery** タグ、ディスク SR/VDI を使って新しい**停止中**のレプリカを特定します。起動しません。次に B、C でそれぞれ前の実行が完了してから繰り返し、実行/レプリカ ID、時刻、元/先ディスク、エラーを記録します。3 回目の前に A/B を特定し、後で保持処理と残ったレプリカを調べます。正常な検証環境では B/C を期待しますが、緑色のジョブ表示だけでデータや削除の原子性を証明しません。
4. 元 VM、C レプリカ、NFS 復元ポイントではなく、保持された**B レプリカ**を選びます。レプリカを停止したまま B プールで固有名の **Fast clone** を作ります。新しい VM/VDI ID とディスク配置を記録し、クローンが停止していて通常の起動を妨げるブロックがないことを確認します。作成に失敗したりクローンがブロックされたままだったりしたら、オブジェクトとエラーを保持して停止し、ブロックを回避しません。停止したクローンから継承した仮想 NIC を**すべて**削除して VIF 一覧が空であることを再確認してから、このクローンだけをコンソール経由で起動し、確認用データを B の SHA-256 と照合します。正常停止します。C を別にクローンして同じ隔離条件で C のハッシュを確認しても構いません。B/C レプリカと独立した NFS バックアップを保持し、[VM の削除手順](/docs/xoa-hl/vm-operations/)で正確に特定した使い捨てクローンだけを整理します。

**合格条件:** 3 回の完全モード実行で元 VM、ターゲットプール/SR、完了したコピーを特定でき、保持後に B/C が残るか差異を説明でき、B の隔離クローンは別の ID、起動前に NIC なし、正確な B の内容を持ちます。インストール済みバージョン、ジョブ/スケジュール、プール/SR/VM/VDI ID、実行 JSON、ブロック状態、保持一覧、チェックサムを記録します。転送、容量、削除、クローン、データ照合が失敗したら追加実行を止め、バックアップ/ストレージ管理者のために一覧を保存します。レプリカの起動ブロックを解除せず、名前だけでポイントを削除せず、バックアップ管理下のスナップショットを削除しません。別プールの管理された DR レプリカでも、元プールの障害や本番切替の検証にはなりません。CR チェーン、予定実行、ネットワーク切替、二重起動防止、フェイルバック、実機の障害復旧は別途検証が必要です。

## 問題がある場合

| 症状 | 確認と次の対応 |
| --- | --- |
| NFS テストが失敗する | アプライアンスからサーバーへの接続、エクスポートパス、権限、マウントオプションを確認します。ブラウザーから NAS に接続できるだけでは不十分です。 |
| バックアップ失敗、または復元ポイントがない | VM とエクスポートのログ、保存先へのアクセスと空き容量、元の SR の空き容量、選択した VM を確認します。スナップショットが残っただけでは目標を満たしません。 |
| 復元ポイントが表示されない | 保存先が有効でエラーがないことを確認し、一覧を更新して、その VM がエクスポートされたか調べます。 |
| 復元が失敗する | ログ、保存先の読み取り、復元先 SR の容量、ホストから SR へのアクセスを確認します。再試行前に途中まで作られた VM がないか確認し、名前だけで削除しないでください。 |
| DR レプリカやクローンが失敗する | 実行と VM/VDI ID、ターゲット SR の容量/接続、ブロック状態を記録します。保持レプリカを停止したままにし、起動ブロックを回避したり保持処理をむやみに再実行したりしません。 |
| 復元 VM にネットワークがない | このテストでは正常です。コンソールのみの確認のため NIC を削除しました。本番ネットワークに接続するにはゲスト IP とサービス識別情報の別途確認が必要です。 |
| ファイルが異なる、または起動しない | 復元ポイントと、バックアップ前にファイルの書き込みが完了していたかを確認します。ログとバックアップを保持し、合格として扱わないでください。 |

実行状態、部分的なエクスポート、確認後の再試行は[バックアップ障害の調査](/docs/xoa-hl/troubleshooting/#backup-failures)を参照してください。
