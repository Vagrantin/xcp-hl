**XOA-HL アプライアンス**の管理者アカウントと、許可されたホストコンソールへのアクセスを用意します。アプライアンスのアドレス、ホストとプールの識別情報、現在の管理担当を記録します。最初の接続は[初回ログインとホスト接続](/docs/xoa-hl/first-login/)を参照してください。

{{< callout type="info" >}}
イメージ `xoa-image-20261009-5f33c81`、パッケージ `v5.113.2_e281c536-ce38`、XO 5.113.2 を対象としたソース確認済みのプレビューです。XO Lite のボタンは `xolite-ce v0.21.0-ce29`（上流 `xo-lite-v0.21.0`）も確認しています。管理移行、古いマーカーとホスト統計の実機テストは未完了です。
{{< /callout >}}

## 1. 接続されたプールを確認する

**設定 → サーバ一覧** (`/#/settings/servers`) を開きます。対象の接続が有効で接続済みであり、一覧に予定したホスト、プール、VM、ストレージが表示されることを確認します。保存された接続情報だけでは接続成功を確認できません。失敗したらエラーを読み、[接続ガイド](/docs/xoa-hl/first-login/)でアドレス、資格情報、証明書の扱いを確認します。

[#126](https://github.com/Vagrantin/xcp-hl/issues/126) に記録されたサポート対象の管理ルールは、**あるホストまたはプールを管理する XOA は 1 台**です。複数のアプライアンスは技術的には接続できますが、同時管理はサポートされません。アプライアンスが 1 つのプールしか管理できないという意味ではありません。接続前に担当を調整し、同じゲストに重複したバックアップスケジュールを残さないでください。

## 2. 別のアプライアンスに管理を移す

1. 作業時間を確保し、実行中の管理とバックアップを完了させ、旧担当の接続、スケジュール、保存先を記録します。[設定をエクスポート](/docs/xoa-hl/configuration-backup/)して保管します。エクスポートだけではジョブを移行または無効化しません。
2. 旧担当の関連スケジュールを無効にします。旧担当の **設定 → サーバ一覧** でプールへの接続を削除してから、新担当を接続します。XO の管理移行のためにホストをプールから外したり VM を削除したりしないでください。
3. 新しいアプライアンスにホストまたはプールへの接続を追加します。接続された一覧と必要な権限を確認します。設定の再作成や復元には、設定ガイドの隔離とインポートの注意事項を適用します。
4. 旧担当が再接続したりプールに対してジョブを実行したりしないことを確認します。保存先を確認し、隔離した復旧テストを行ってから、新担当の予定したスケジュールだけを有効にします。

どちらかの状態が不明なら移行を中断し、接続やタスクのエラーを保存します。この手順はプールの構成を変更しません。別の 2 ホスト参加試行を後述しますが、HA とライブマイグレーションは対象外です。

## 3. XO Lite のボタンを理解する

XO はプールの `other-config` に `xo:clientInfo:<appliance-uuid>` を書き込みます。初期設定では接続時と **6 時間**ごとに更新し、その更新時に **48 時間**より古いマーカーを削除します。読み取り専用の XO 接続では書き込みません。接続を削除すると将来の書き込みは止まりますが、古いマーカーはすぐには消えません。

確認した XO Lite では、**Access XOA** は `lastConnected` が最も新しいマーカーを使います。`publicUrl` を優先し、なければ `eth0`（または最初の利用可能なインターフェース）の最初のアドレスを HTTPS で開きます。VM や Web サービスの稼働は確認しません。アドレスが見つからなければ **Deploy XOA** を表示します。XO Lite 自体は古いマーカーを期限切れにしないため、XO が接続しなければ古いボタンが残る場合があります。

古いアドレスを理由に 2 台目の管理アプライアンスを展開しないでください。既知のアドレスと管理担当を先に確認します。正しい担当が誤ったアドレスを公開しているなら、マーカーを繰り返し削除するのではなく URL やネットワーク設定を確認します。

## 4. 古いマーカーを確認して削除する

**ハイパーバイザーホスト**で root 権限を使い、まず次の読み取り専用コマンドを実行します。管理記録と照合し、プールと古いキーを正確に特定します。

```bash
xe pool-list params=uuid,name-label
xe pool-param-get uuid='<pool-uuid>' param-name=other-config
```

旧アプライアンスの接続を削除した後に限り、マーカーの値を記録し、必要なら**そのキーだけ**を削除します。両方のプレースホルダーを置き換えてください。`other-config` 全体を削除してはいけません。

```bash
xe pool-param-remove uuid='<pool-uuid>' param-name=other-config param-key='xo:clientInfo:<obsolete-appliance-uuid>'
```

読み取り専用の確認を繰り返し、XO Lite を再読み込みします。旧担当がまだ動いていれば、再接続時や次の更新でマーカーを書き戻す場合があります。キーが戻ったら、残っている接続を調べます。この操作は検出用メタデータを変更し、プール構成、VM の電源、バックアップデータは変更しません。今回のソース確認では実行していません。

## 5. ホスト統計を読む {#host-statistics}

この観察練習では、ホスト、VM、ネットワーク、ストレージの設定を変更しません。既知の接続済みで実行中のホストを使い、ID、プール、CPU 数とメモリ容量を記録します。そのホストの **状態** タブ (`/#/hosts/<id>/stats`) を開き、グラフを読む前に対象の識別情報を確認します。プールの概要やアプライアンス自身の OS モニターとは対象範囲が異なります。

1. 初期値の **10分前まで表示** から始めます。選択した期間、現在時刻、ブラウザーのタイムゾーン、表示された最新サンプル時刻とタスク・接続エラーを記録します。予定したサンプリング間隔を数回分待ち、新しいデータが届くことを確認してください。グラフが画面に残っているだけでは、収集が最新であるとは判断できません。
2. セレクターで長い期間と比較します。確認したサーバーは **AVERAGE** サンプルを要求するため、長い期間の 1 点では短いピークが平均化されることがあります。短い期間に戻すと直近の変化を調べやすくなります。期間名は要求する履歴を示し、ホストが期間全体の履歴を保持していることは保証しません。

| 期間の表示名 | 想定されるサンプル間隔・タブの更新間隔 |
| --- | --- |
| 10分前まで表示 | 5 秒 |
| 2時間前まで表示 | 1 分 |
| Last day | 1 時間。直近 24 個の時間単位サンプル |
| 1週間前まで表示 | 1 時間 |
| 1年前まで表示 | 1 日 |

この版の **Last day** は英語表示のままです。長期間の表示が 5 秒ごとに更新されるとは限りません。同じ期間とサンプル間隔で比較し、最後の点を瞬時値として扱わずに表示時刻を記録します。

3. 最初は **Stacked values** をオフにして個別の系列を読み、必要なら意図的に切り替えて比較します。その都度、凡例、表示単位と縦軸を確認してください。この切り替えは CPU・ネットワークの合計系列を追加し、軸の範囲も変えることがあります。

| グラフ | 読み方と制限 |
| --- | --- |
| CPU利用量 | 個々の `Cpu` 系列はパーセントです。`All Cpus` はそれらの合計で、正規化したホスト全体の使用率ではありません。4 個の CPU が各 50% なら合計は 200% です。飽和と判断する前に CPU 数と個別の系列を確認します。 |
| メモリ利用量 | ホストの総メモリから空きメモリを引き、バイト単位のサイズで表示します。ゲストの設定済みメモリ上限やアプリケーションの空き RAM ではありません。確認したソースでは空きメモリのデータがないと使用量がゼロに見える場合があるため、予期しないゼロは独立した方法で確認します。 |
| ネットワーク転送量 | 番号付き `eth` の受信 (`rx`)・送信 (`tx`) 系列を読み、ホストのインターフェース一覧と照合します。表示はバイト単位のサイズ表記で、この練習は Mbps・Gbps への換算やボンド・VLAN の網羅性を検証しません。静かな系列だけではリンクの正常性やゲストの接続を判断できません。 |
| Load average | ホストの別の `loadavg` メトリックです。CPU パーセントやディスク容量の直接的な指標ではありません。CPU、メモリ、通信と実際のワークロードを照合します。ここでは普遍的な正常範囲のしきい値を定めません。 |

4. 既知の通常ワークロードで基準を記録し、同じホスト・期間・設定で特定済みの活動時間と比較します。対象系列、時刻、サンプル間隔と実際の症状を保存します。グラフを動かすためだけに、本番で負荷試験を行ったりゲストをリサイズ・移行・再起動したりしないでください。検証用ワークロードには、別途オペレーターの許可が必要です。

**No stats.**、読み込みが終わらない状態、欠損や予期しない平坦・ゼロ表示があれば、対象ホスト、期間、時刻とエラーを保存します。接続と実行状態を確認してからページを再読み込みし、短い期間を選び直します。確認したタブはホストが実行中でなければ取得せず、取得失敗で待機状態が残る場合もあります。待つだけでは収集が再開しないことがあります。また、一部の欠損値は変換時にゼロになります。空のグラフやゼロは、ホストが無活動または正常であることを示す証拠ではありません。時刻が進まない場合は、容量の判断前に[トラブルシューティング](/docs/xoa-hl/troubleshooting/)と、許可されたホストの独立した観察を行います。この練習の復旧手順として統計をリセットしたり本番ホストを再起動したりしません。

この練習はホストのグラフを読む範囲に限ります。実機でのメトリックの正確さ、全履歴、時計の一致、通知・しきい値、ダッシュボード・プールの集計、SR 容量と性能診断には個別の受け入れ確認が必要です。これらのグラフだけでは、追加 VM の余裕、HA フェイルオーバーや安全な移行は確認できません。

## 6. 使い捨てホスト 1 台のプール参加を試行する {#pool-join}

この**ソース確認済みプレビュー**は、イメージ `xoa-image-20261009-5f33c81`、パッケージ `v5.113.2_e281c536-ce38` の XO 5.113.2 を対象とします。参加はホストの所属を変更し、不足するパッチをインストールする可能性があります。再構築でき、リリースを特定した実験用ホスト 2 台だけを使います。参加先は 1 ホストプールのマスター、参加元は別の 1 ホストプールの唯一のホストです。独立したコンソール、記録済みの復旧・再構築計画と、両接続を担当する XOA-HL 1 台を確保します。稼働中の本番プール、HA、実行中のゲスト、共有または接続済みのワークロード、独立したバックアップのないデータは対象外です。

1. **XOA-HL のブラウザー**で **設定 → サーバ一覧** を開き、各 1 ホストプールへの接続が動作することを確認します。両プールの ID、参加先マスターと参加元ホストの ID、製品ブランド、バージョン・ビルド・パッチ、管理アドレス、ネットワーク・ストレージ一覧、VM 数、実行中のジョブを記録します。作業中は双方のバックアップスケジュールを止め、独立した復旧点を保持します。単独ホストも 1 ホストのプールに属します。参加元プールに別のホストがないことを確かめます。ネットワーク・ストレージの担当者と、同一ネットワーク上での参加構成、DNS と時刻の同期、個別の管理接続、コンソールからの復旧を確認します。同じ名前のネットワークや SR が共有されていると推測しないでください。
2. **参加先プール**のページ (`/#/pools/<target-pool-id>/general`) でマスターを確認し、**Add hosts** を開きます。予定した参加元ホスト 1 台だけを選択します。選択欄は複数ホストのプールに属するホストを除外し、双方向のパッチ差分を表示します。いずれかの差分数がゼロでない場合、ブランド・バージョンが異なる場合、HA が有効な場合、参加元の VM や SR を保持する必要がある場合、参加経路が不明な場合は**キャンセル**し、この試行の外で条件を整理します。この画面をパッチ適用やホスト退避の近道にしないでください。ソース上、UI は `force: true` を送信し、XAPI の `pool.join_force` を呼びます。確定操作は状態を変更し、互換性だけを調べる操作ではありません。
3. 事前確認を記録し、承認済みの作業時間内に参加先プールと参加元ホストを照合して一度だけ確定します。成功後は参加元の接続が登録解除され、参加先の一覧が更新される想定です。一時的に切断された表示になることもあります。タスクや画面の更新が遅いだけで再送信しないでください。失敗時はタスク・エラー、コンソールの状態、双方の一覧を保存します。サーバー側では既にパッチ処理や参加の一部が進んでいる可能性があります。再度強制参加やホスト排出をせず、担当者の復旧計画に従います。
4. 参加先の接続を更新します。プール ID とマスターが予定どおりで、予定した 2 つのホスト ID が所属し、元のプールと接続の状態が説明できることを確認します。各ホストのネットワーク・PIF、SR・PBD の接続、管理経路を確認し、テスト用ストレージと隔離したゲストネットワークが適切なホストから使えることを検証します。意図しない VM、重複した XOA 接続、バックアップジョブや XO Lite 管理マーカーも調べます。所属だけで安全な移行や HA の可否は判断できません。

操作前後の ID、パッチ差分数、タスク結果、各コンソールへの到達性、各確認項目の成否を記録します。参加後の実験用構成が目的なら維持します。**Detach/eject** は別の状態変更であり、自動的なロールバックではありません。インストール環境での参加・パッチ・ネットワーク・ストレージの挙動、失敗後の復旧、後のホスト削除、HA、共有ストレージ、ライブマイグレーション、人による EN/FR/JA の確認は未完了です。
